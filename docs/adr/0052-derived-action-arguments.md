# 0052. Аргументы действий — **генерируемая из игры** таблица, имя — подпись диалога самой игры

- Status: accepted
- Date: 2026-11-28
- Supersedes: —
- Amends: [0051](0051-action-argument-hints.md) — §1 «таблица по id действия, написанная

  `tools/scan-action-parameters.ps1` (генератор: обход цепочки диалогов, отбрасывание диалога

## Context

### 1. Что сказал владелец продукта

После второй проверки в игре, на блоке **Action Relay** и его действии «Set Channel and Send
Signal»:

1. поле по-прежнему называется «Text» — «проблема решена локально, а не системно»;
2. название параметра **должно быть получено из игры**, «из описания»; если привязывать
   действие через игру, она показывает человеко-понятное описание;
3. **непонятно, какие ещё действия в каких блоках не охвачены** «описаниями параметров»;
4. отдельно: линия связи продолжает следовать за курсором и после выбора действия, и при
   открытой форме параметров — «создаёт ощущение, что связь будет создана как-то неправильно».
   После клика по карточке линия должна «временно» идти прямо к карточке, символизируя, что
   связь с блоком уже есть.

ADR-0051 закрыл пункт 1 только для четырёх известных действий и не отвечал на пункт 3 вовсе.
Это и есть «локально, а не системно».

### 2. Что игра на самом деле знает — проверено по IL и по её таблицам текста

| Факт | Чем проверено |
|---|---|
| `ParameterDefinitions` для встроенных действий — заглушка `TerminalActionParameter.Empty` | `dump-se-il.ps1 -Type 'Sandbox.Game.Entities.Cube.MyMotorStator' -Method 'CreateTerminalControls'` |
| **настоящий тип** аргумента — `unbox.any` обработчика (или хелпера, который он зовёт) | `OnRotateToAngleApplied`: `unbox.any Single, Single, Int64`; `OnSetChannelApplied`: `unbox.any Int32`; `OnSetBlinkIntervalApplied` → `TryGetFloatFromCapturedParam` → `unbox.any Single` |
| **имя параметра** — подпись диалога, который игра строит для этого параметра | `RequestRotationParametersAndLabel` строит **цепочку** диалогов: `BlockActionTitle_SetAngle` → `BlockActionTitle_SetVelocity` → `BlockActionTitle_SetRotationDirection` |
| у каждого действия есть **ещё один** диалог — метки тулбара, и он не параметр | `SetValue_Action_SetLabel`; его обработчик подтверждения вызывает `SetCustomIconTitle` |
| часть действий грузит подпись **в самой регистрации**, а не в методе запроса | `ldstr 'SetVelocity'; ldsfld BlockActionTitle_SetVelocity; ldftn OnSetVelocityApplied` |
| **один диалог может заполнять несколько параметров** | `SetColor` объявляет `Int32, Int32, Int32`, но спрашивает одним `MyGuiScreenDialogColor` с подписью «Set Color» |
| ключи подписей есть в таблицах текста игры, на всех её языках | `MyTexts.resx`: `BlockActionTitle_SetRotationDirection = Set Rotation Direction` |

Полный разбор с IL — [`01-research/api-action-parameters.md`](../01-research/api-action-parameters.md) §2.5–2.9.

### 3. Почему первая версия была хаком и что именно она делала не так

Первая версия (внутри этого же ADR, до правки) читала **один** метод запроса и брала **одну**
подпись. Этого хватило ровно на первый параметр ротора. Дальше:

| Что вышло | Почему | Как выглядело для игрока |
|---|---|---|
| второй и третий параметр ротора | подписи лежат в **замыканиях** диалогов, а не в методе запроса | «Number 2», «Number 3» — заглушки |
| третий параметр стал бы «Set label» | в цепочку попадал диалог **метки тулбара** | поле называлось бы именем метки |
| у Action Relay имя = имя действия | подпись не находилась, срабатывал откат «подпись действия для одного аргумента» | «Set Channel and Send Signal» вместо «Set Channel» |
| у `SetColor` было бы три поля | не учитывалось, что один диалог заполняет три параметра | два выдуманных имени из трёх |

Все четыре — следствие одного и того же: **читался не тот код, который игра исполняет**.
Откат «взять подпись действия» выглядел разумным, но он и есть обходной путь: он даёт
правильный ответ только тогда, когда имя параметра случайно совпадает с именем действия.
## Decision

### 1. Таблица генерируется, а не пишется

`tools/scan-action-parameters.ps1` читает установленные сборки и выдаёт
`Model/ActionParameterTable.g.cs`:

- **тип** каждого аргумента — `unbox.any` обработчика действия, в порядке аргументов;
- **подпись** — поля `MyStringId`, загружаемые методом запроса, разрешённые в текст через
  `MyTexts.resx` и `MyTexts.ru.resx` игры;
- значения-образцы (`"Dist:{0}"`) отбрасываются: это шаблон подписи элемента, а не имя.

`offline-check.ps1` **перезапускает генератор и сравнивает результат побайтово** с
закоммиченным файлом — ровно так же, как `build-icon-atlas.ps1 -Verify` для иконок. Значит:

- таблица не может разойтись с игрой незаметно;
- ручная правка таблицы роняет шлюз — то есть «дописать от себя» технически нельзя;
- после обновления игры достаточно запустить генератор.

### 2. Имя поля — подпись диалога, который игра показывает для этого поля

`ParameterSpec.Name` — **подпись диалога из игры**, и порядок источников такой:

1. подпись диалога, построенного методом запроса действия (обход **транзитивный**: через
   замыкания `OnConfirmed`, потому что диалоги строятся цепочкой);
2. подпись, которую регистрация действия передаёт общему диалогу значения — часть действий
   грузит `MyStringId` прямо в `CreateTerminalControls`;
3. ничего третьего нет. Если игра не назвала поле, поля нет: у такого действия нет и диалога.

**Откат «взять имя действия» удалён.** Он давал правильный ответ только там, где имя параметра
случайно совпадает с именем действия, и именно из-за него Action Relay показывал название
действия вместо названия параметра. Форма больше не подставляет `ActionCaption` вместо имени:
если `Name` пуст, это дефект таблицы, и `offline-check.ps1` его ловит отдельной проверкой по
всем 22 действиям.

**Диалог метки тулбара отбрасывается — по поведению, а не по имени.** У каждого
параметризованного действия есть диалог метки (`SetValue_Action_SetLabel`), и его нельзя
считать параметром. Признак — его обработчик подтверждения вызывает `SetCustomIconTitle`;
обработчики параметров этого не делают.

### 3. Один диалог — одно поле, сколько бы параметров он ни заполнял

`SetColor` объявляет три `Int32`, но спрашивает их **одним** выбором цвета с подписью
«Set Color». Форма рисует **одно** поле: три поля вынудили бы придумать два названия, которых в
игре нет, — ровно то, что запрещено.

Значения вводятся через запятую, число значений проверяется, и в подсказке под полем написано,
сколько их. Разбиение выводится из двух счётчиков, которые игра даёт сама (подписей и
параметров), а не задаётся таблицей.

### 4. Тип пишется точный

`ParameterSpec` хранит **точный** `TypeCode` из таблицы, а не «число вообще». Это не
педантство: обработчик канала делает `unbox.any Int32`, и значение, записанное как `Int64`,
он прочитать не сможет. Шлюз это и поймал — первая версия `SpecFor` подменяла `Int32` на
`Int64`.

Тип берётся не только из `unbox.any` самого обработчика: часть обработчиков приводит значение
через хелпер (`TryGetFloatFromCapturedParam`) или через `Convert.ToSingle`, а часть передаёт
значение прямо в сеттер (`MyBeacon.SetHudText(String)`). Обход идёт и туда — это тот же код,
который игра исполняет, а не догадка о нём.

**Тип выведен у 21 действия из 22.** У `GpsList` ни один источник не дал ответа: его
`OnAction` читает список параметров, но передаёт его в `FillGpsList`, а единственный
`unbox.any` в нём — собственный enum `Direction`. Поэтому тип остаётся объявленным, и действие
попадает в лог покрытия. Подставить догадку было бы возвратом к тому же: неверный тип — это
связь, которая не срабатывает.

### 5. Покрытие — факт, а не обещание

`ActionParameterHints.HasKnownTypes(actionKey)` отвечает, описано ли действие **с известным
типом**. Если нет — экран пишет в лог строку с id действия, один раз на id:

```
[VGS] action 'X' declares arguments this build does not describe; values are written with the declared type
```

Так на вопрос «какие ещё не охвачены» отвечает лог после одной сессии, а не догадка в
документе. Список всех 22 известных действий — в research-заметке §2.5.

### 6. Линия привязки принадлежит карточке, а не курсору

Жест состоит из двух половин: «какой блок» и «какое действие, с какими значениями». Как только
игрок кликнул по карточке, первая половина отвечена — и линия перестаёт следовать за курсором:

- `_bindTarget` запоминает выбранную карточку;
- линия идёт от точки источника **к центру этой карточки**, без диска под курсором (карточки
  рисуются после линий, поэтому видимый конец — её граница: «связь с этим блоком»);
- линия остаётся на месте, пока открыто меню действий и пока открыта форма параметров;
- линия исчезает вместе с привязкой: «Отмена», Esc, клик по пустому месту, неудачная запись —
  всё это `CancelBind()`, и он же сбрасывает `_bindTarget`.

Точка назначения — центр карточки, а не порт: порта ещё нет (полоса входа появляется с первым
ребром), а линия в реальный порт назвала бы действие, которого игрок не выбирал.
## Alternatives

**1. Дописать Action Relay в таблицу руками.** Отклонено: это ровно то, что владелец продукта
назвал «локально, а не системно». Через месяц нашлось бы ещё одно действие.

**2. Держать таблицу в JSON и читать в рантайме.** Отклонено: мод не может поставить файл рядом
с `.cs` (игра компилирует только скрипты), а `MyModStorageComponent` — не место для констант
игры. Сгенерированный `.cs` — это тот же JSON, но проверяемый компилятором.

**3. Читать IL игры в рантайме.** Отклонено: тела методов игровых сборок моду недоступны,
а свой интерпретатор IL внутри мода — это второй проект.

**4. Вызвать ванильный диалог через `DoUserParameterRequestWithItem`.** Отклонено: это и есть
последовательный ввод, который владелец продукта просил не повторять; плюс `Sandbox.Graphics`
вне вайтлиста, плюс диалог перекрыл бы редактор.

**5. Переводить подписи аргументов самим.** Отклонено: подписи уже есть в таблицах текста игры
на всех её языках, и генератор их забирает. Свой перевод — это второй источник истины, который
разойдётся с первым.

**7. Дописать имена руками по образцу известных.** Отклонено по той же причине, что и (1), и
именно это было первой версией: она дала «Number 2», «Number 3», «Set Channel and Send Signal»
и два выдуманных имени из трёх у цвета. Имя, которого нет в игре, — это заглушка, даже если оно
выглядит правдоподобно.

**6. Рисовать линию привязки к порту-приёмнику.** Отклонено: у действия ещё нет полосы
(она появляется с первым ребром), и линия в произвольный порт утверждала бы выбор действия.

## Consequences

Легко:

- **добавить действие** — запустить генератор; имена и типы приходят сами;
- **проверить, что таблица верна** — `offline-check.ps1` сравнивает с игрой;
- **узнать покрытие** — по логу и по research-заметке;
- **новое действие с одним аргументом** работает без всякой таблицы: имя даёт игра.

Трудно:

- **генератор — мини-дизассемблер.** Он читает IL линейно и опирается на то, что
  `CreateTerminalControls` — прямолинейный код. Если игра перепишет регистрацию в цикл или
  вынесет её в helper, генератор найдёт меньше действий; признак — уменьшившееся число строк
  в таблице, и шлюз это покажет как расхождение;
- **12 из 22 действий остаются с объявленным типом** (их обработчики приводят значение через
  неявное преобразование, а не `unbox.any`), и это видно в логе как «не описано». Это честное
  состояние, а не забытое;
- **подписи аргументов — английские и русские из игры**, потому что генератор берёт только эти
  две таблицы. Для других языков игры подпись будет английской, как и весь остальной мод
  (ADR-0033).

Запрещено:

- **править `ActionParameterTable.g.cs` руками** — шлюз сравнивает его с игрой;
- **брать тип из `ParameterDefinitions`**, когда действие описано;
- **подменять точный `TypeCode` «похожим»** (`Int32` → `Int64`): обработчик делает
  `unbox.any` конкретного типа;
- **возвращать линию привязки к курсору после выбора карточки**;
- **обещать покрытие в документе, не проверив его логом**.

## Verification

Шлюзы:

```powershell
& .\tools\verify-compile.ps1      # COMPILE OK — 79 file(s), 0 warning(s)
& .\tools\check-whitelist.ps1     # WHITELIST OK
& .\tools\review-check.ps1        # REVIEW OK — no findings
& .\tools\offline-check.ps1       # OFFLINE OK, в том числе ACTION PARAMETER TABLE OK
& .\tools\scan-action-parameters.ps1   # 22 действия с типами и подписями
```

Офлайн проверяется, в частности:

- **ни одного выдуманного имени**: для всех 22 описанных действий каждое поле имеет `Name`, и
  проверка падает, если хоть одно пустое;
- три поля ротора имеют **три разных** имени, и первое — «Set Angle» (и его русский вариант);
- поле Action Relay называется **«Set Channel»**, а не именем действия;
- `SetColor` — **одно** поле с `Slots == 3`, ввод «10, 20, 30» даёт три параметра по порядку,
  а «10, 20» и «10,,30» **отклоняются** (а не дополняются нулём);
- подсказка для такого поля существует и принимает число;
- типы: ротор `Single, Single, Int64`, канал `Int32` (а не объявленный текст),
  `SetChannelValue_SendSignal` — один `Int32`, `Run` — `String`, `SetDelay` — `Single`;
- таблица совпадает со свежим сканом сборок побайтово.

Человек в игре:

1. **Ротор, Rotate to Angle.** Три поля и три **человеческих** названия: «Set Angle»,
   «Set Velocity», «Set Rotation Direction». Ни одного «Number N».
2. **Action Relay, Set Channel and Send Signal.** Поле называется «Set Channel» — **не** так,
   как действие. Ввод числа создаёт работающую связь.
3. **Свет, Set Color.** Одно поле «Set Color», в него вводятся три числа через запятую;
   подсказка говорит, сколько их. Два числа не создают связь.
4. **Маяк, Set HUD Text.** Поле называется «Set HUD Text», принимает текст.
5. **Таймер, Set Delay.** Поле «Set Delay», принимает число.
6. **Недопустимое значение** (буква в числовом поле) не создаёт связь.
7. **Линия привязки.** Начать привязку, кликнуть по карточке — линия **сразу** идёт к карточке
   и больше не следует за курсором, ни в меню действий, ни в форме параметров.
8. **Отмена на любом шаге** — линия исчезает, связи нет.
9. **Успешная привязка** — линия заменяется настоящей связью без скачка.
10. **Покрытие.** В логе нет строк `declares arguments this build does not describe` ни для
    одного действия из списка §2.5.
11. В логе нет `prohibited`.
