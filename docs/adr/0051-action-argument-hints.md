# 0051. Аргумент действия описывается проверенной таблицей: имя, тип, допустимые значения, значение по умолчанию

- Status: accepted
- Date: 2026-11-27
- Supersedes: —

  полем в окне. Шлюзы зелёные; приёмка в игре — за человеком (§Verification).

## Context

### 1. Что сказал владелец продукта после первой проверки в игре

Четыре замечания, все про одно окно:

1. поля называются «Text 1», «Text 2», «Text 3» — нужны человеческие имена;
2. у второго аргумента есть значение по умолчанию — редактор должен его подставлять;
3. третий аргумент ротора в игре — выпадающий список; пусть вводится числом, но надо
   понимать, что выбираешь;
4. **редактор создал связь с неправильными параметрами, и она не работала** — так быть не
   должно.

Четвёртое — не пожелание, а дефект, и он объясняет первые три.

### 2. Почему связь оказалась мёртвой — проверено по IL

ADR-0050 §2 исходил из того, что игра публикует типы аргументов, и проверять надо диапазон
типа. Это верно наполовину: игра публикует **список типов**, но для встроенных действий
заполняет его заглушкой.

`MyMotorStator.CreateTerminalControls` для `RotateToAngle`
(`dump-se-il.ps1 -Type 'Sandbox.Game.Entities.Cube.MyMotorStator' -Method
'CreateTerminalControls'`):

```
0BF3: ldsfld   Empty                      <-- TerminalActionParameter.Empty
0BF8: call     TerminalActionParameter::Get
0BFD: callvirt List`1::Add                <-- три раза
```

`TerminalActionParameter.Empty` — это `default(TerminalActionParameter)`, `TypeCode ==
TypeCode.Empty`. То есть **типа в метаданных нет вообще**, а не «тип не тот».

Обработчик того же действия (`dump-se-il.ps1 -Method 'OnRotateToAngleApplied'`) читает
`Single`, `Single`, `Int64` и на первом несовпадении делает `ret` — молча ничего не делает.

Отсюда ровно тот исход, который увидел игрок: элемент записан с типом `Empty`/`String`,
тулбар его показывает, действие по нему не срабатывает.

Полный разбор — [`01-research/api-action-parameters.md`](../01-research/api-action-parameters.md) §2.

### 3. Почему нельзя прочитать имена, значения по умолчанию и списки из игры

Имена аргументов игра держит в локализованных строках своих диалогов
(`BlockActionTitle_SetAngle`, `…SetVelocity`, `…SetRotationDirection`), значения по
умолчанию — в аргументах конструкторов `MyGuiScreenDialogAmount` и в состоянии блока,
список направлений — в `MyGuiScreenDialogEnumDropdown<MyRotationDirection>`. Ни одно из
этих мест моду недоступно: диалоги живут в `Sandbox.Graphics.GUI` и `Sandbox.Game.Screens`,
которых нет в вайтлисте. Значит нужное знание должно быть **записано** — но записано так,
чтобы не стать той таблицей подтипов, которую убрал ADR-0011.

## Decision

### 1. Таблица по **id действия**, а не по подтипу блока

`Model/ActionParameterHints.cs` описывает аргументы действия по его id — стабильному
идентификатору, который игра публикует, а мод уже хранит в элементе тулбара. Одна запись
обслуживает все блоки, у которых это действие есть (ротор и hinge делят `RotateToAngle`).

Три правила, которые не дают таблице стать той, что убрал ADR-0011:

1. **Она ничего не скрывает.** Число аргументов всегда равно
   `ParameterDefinitions.Count`. Запись таблицы сверх этого числа игнорируется, а действие
   без записи работает как раньше — с типами из метаданных.
2. **Она не выводится из имени блока.** Ключ — id действия, не подтип.
3. **Каждая запись добыта из кода игры** и записана вместе с командой, которая её
   доказывает ([`01-research/api-action-parameters.md`](../01-research/api-action-parameters.md)
   §2.2). Ничего «по аналогии».

### 2. Что описывает запись

`ParameterSpec` (Model): `Type` — настоящий тип, с которым значение пишется в элемент;
`Kind` — что принимает поле (`Text`, `Number`, `WholeNumber`, `Choice`); `NameKey` — ключ
имени в таблицах строк; `DefaultFrom`/`DefaultText` — значение по умолчанию; `Min`/`Max` —
границы, если они известны; `Choices`/`ChoiceKeys` — допустимые значения и их смысл.

Описаны: `Run` (аргумент скрипта), `RotateToAngle` (угол, скорость, направление),
`SetVelocity`, `SetLowerLimit`, `SetUpperLimit`. Всё остальное — прежнее поведение.

### 3. Проверка значения — то, что объявлено для аргумента

`ParameterSpec.TryValidate` — единственное место, где решается, годится ли введённое. Три
отказа, и они разные, потому что игроку нужно разное действие:

| Отказ | Когда | Что сказать |
|---|---|---|
| `Invalid` | текст не читается как нужное (`abc` в числе, `cw` в направлении) | «значение не того типа» |
| `OutOfRange` | число того же вида, но вне границ аргумента (`1000` для угла ротора) | «вне диапазона» |
| `NotAllowed` | число верное, но такого значения у аргумента нет (`7` для направления) | «не из допустимых: 0, 1, 2» |

Запись в тулбар происходит **только** после того, как все поля прошли проверку, поэтому
мёртвая связь из окна больше не создаётся — это и есть исправление четвёртого замечания.

### 4. Список значений виден, вводится числом

Направление ротора — `Choice` с тремя значениями `0`, `1`, `2`. Игрок вводит число, а под
полем стоит строка «допустимо: 0 — авто, 1 — по часовой, 2 — против часовой». Смысл берётся
из имён перечисления (`MyRotationDirection`: `AUTO`, `CW`, `CCW`, проверено рефлексией) и
переводится.

**Почему не выпадающий список.** Свой список — это новый контрол: своя геометрия, свой
hit-test, своё раскрытие, своя прокрутка, и всё это внутри окна, которое уже рисуется поверх
игрового экрана. Требование владельца продукта прямо разрешает ввод числом («пускай даже
игроку потребуется вводить 0, 1 или 2»), а строка под полем закрывает вопрос «что именно
выбираешь». Список — отдельная работа, записанная в ROADMAP.

### 5. Значение по умолчанию — из блока, а не из константы

`Game/ActionParameterDefaults.cs` читает то, что игра сама подставила бы:

- `Run` → `IMyProgrammableBlock.TerminalRunArgument` (последний аргумент скрипта; ради него
  у блока есть второе действие, `RunWithDefaultArgument`);
- скорость ротора → `IMyMotorStator.TargetVelocityRPM` (в RPM — ровно в тех единицах,
  которые принимает обработчик);
- пределы ротора → `LowerLimitDeg` / `UpperLimitDeg` (геттеры вызывают
  `MathHelper.ToDegrees` — проверено по IL);
- угол и направление — литералы из таблицы (`0` и `0`, то есть «на месте» и «авто»).

У группы нет одного блока, поэтому её поля открываются пустыми — и это честно: подставлять
значение «первого участника» значило бы обещать то, чего группа не делает.

### 6. Имя поля — из таблицы, иначе из вида значения

Имя берётся из `NameKey` (переводится через `VgsText.ParameterName`). Если записи нет —
прежнее «Число 2», и это не заглушка, а точное описание того, что известно: игра о таком
аргументе не сообщила ничего, кроме типа.

## Alternatives

**1. Прочитать типы из IL в рантайме.** Отклонено: мод не имеет доступа к телам методов
игровых сборок (рефлексия по `MethodBody` в вайтлисте скриптов недоступна), а разбор IL
своими руками — это интерпретатор .NET внутри мода.

**2. Вызвать ванильный диалог игры** (`DoUserParameterRequestWithItem` /
`RequestParameterCollection`) и забрать готовый элемент. Отклонено: это ровно тот
последовательный ввод, который владелец продукта просил не повторять, плюс игровой экран
поверх нашего.

**3. Хранить типы по подтипу блока** («ротор — Single, Single, Int64»). Отклонено: подтипов
десятки, действия общие, и таблица подтипов — это дефект, который убрал ADR-0011. Ключ —
id действия.

**4. Не проверять вовсе, а показывать предупреждение после записи.** Отклонено: владелец
продукта сказал «этого не должно быть». Предупреждение после записи — это и есть «связь
создана и не работает».

**5. Свой выпадающий список для `Choice`.** Отложено, не отклонено: требование разрешает
ввод числом, а список — отдельный контрол (см. §4).

## Consequences

Легко:

- **добавить действие в таблицу** — одна запись, и оно сразу получает имена, типы, границы и
  умолчания; офлайн-шлюз проверяет, что у каждой записи есть переводы;
- **проверить правило офлайн** — `ParameterSpec`, `ActionParameterHints`, `ParameterForm` не
  трогают игру, поэтому `tests/OfflineChecks.cs` проверяет и таблицу, и отказы, и
  предзаполнение без запуска игры.

Трудно:

- **таблица может отстать от игры.** Обновление игры может поменять типы аргументов, и
  тогда мод начнёт отклонять значения, которые игра принимает. Признак — отказ на значении,
  которое ванильный диалог принимает; лечится сверкой IL по команде из research-заметки;
- **сторонние действия не описаны**, и для них остаётся прежнее правило: тип из метаданных.
  Если чужой мод объявляет заглушку, его связь может не сработать — угадать его типы мод не
  может (помечено `[НЕ ПРОВЕРЕНО]` в research-заметке);
- **границы известны не для всех аргументов.** Для угла ротора взят запасной диапазон самой
  игры (±360°, когда определение мотора своего не объявляет); hinge с более узким
  диапазоном получит значение, которое игра ограничит сама.

Запрещено:

- **брать тип аргумента из `ParameterDefinitions` для действия, у которого есть запись в
  таблице.** Для встроенных действий там заглушка, и запись с ней — мёртвая связь;
- **добавлять запись в таблицу без команды, которая её доказывает.** Запись — это факт о
  чужом коде, а не догадка;
- **менять число аргументов таблицей.** Аритмия — игра;
- **подставлять в группу значения «первого участника»**.

Если решение окажется неверным (таблица мешает), откат — убрать запись действия из
`ActionParameterHints.Row`: действие вернётся к поведению ADR-0050 без правок в остальном
коде.

## Verification

Шлюзы (зелёные на момент реализации):

```powershell
& .\tools\verify-compile.ps1      # COMPILE OK — 78 file(s)
& .\tools\check-whitelist.ps1     # WHITELIST OK — 243 distinct type reference(s)
& .\tools\review-check.ps1        # REVIEW OK — no findings
& .\tools\offline-check.ps1       # OFFLINE OK — 3131 checks
```

Офлайн проверяется: таблица (три аргумента ротора, их настоящие типы `Single`/`Single`/
`Int64`, три значения направления и их смысл, имена переведены в обоих языках, аритмия
берётся у игры, незнакомое действие сохраняет объявленный тип и не получает выдуманного
имени), отказы (`abc` → `Invalid`, `1000` → `OutOfRange`, `-1` для скорости → `OutOfRange`,
`7` для направления → `NotAllowed`, `cw` → `Invalid`, пустая строка для скрипта допустима),
предзаполнение (направление `0`, угол `0`, пустая скорость честно называется как незаполненное
поле, значение блока перекрывает литерал, правка начинается со значений связи, значение
чужого типа отбрасывается), и наличие строк подсказки и отказа в таблицах.

Человек в игре:

1. **Ротор `RotateToAngle` — три имени.** Окно показывает «Угол, °», «Скорость»,
   «Направление», а не «Text 1/2/3».
2. **Значение по умолчанию.** Поле «Скорость» заполнено скоростью, с которой ротор крутится
   сейчас (или максимумом, если стоит). Поле «Направление» — `0`.
3. **Список виден.** Под полем «Направление» написано «допустимо: 0 — авто, 1 — по часовой,
   2 — против часовой».
4. **Неправильное значение не создаёт связь.** Ввести в «Угол» `1000` или в «Направление»
   `7`, нажать «ОК» — окно не закрылось, поле обведено, внизу причина; связи нет, в тулбаре
   пусто.
5. **Связь с правильными значениями работает.** Угол `45`, скорость `5`, направление `1` —
   ротор поворачивается на 45° по часовой стрелке с этой скоростью.
6. **`Run` подставляет последний аргумент.** Programmable block, который запускали со
   строкой `scan`, открывает окно с `scan` в поле.
7. **Группа.** Связь на группу роторов: поля открываются пустыми (значения группы не
   выдумываются), и связь создаётся только после заполнения.
8. **Чужое действие.** Действие из другого мода с аргументом: поле называется по виду
   значения, ничего не выдумано, связь пишется как раньше.
9. В логе нет `prohibited`; в окне нет ключей вида `PARAMETER_…`.
