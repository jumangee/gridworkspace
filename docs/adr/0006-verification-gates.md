# 0006. Шлюзы: компиляция и статическое ревью

- Status: accepted
- Date: 2026-11-19
- Supersedes: —

## Context

Игра сама компилирует исходники мода, поэтому обычная сборка ничего не доказывает:
ошибка обнаруживается только при запуске игры. Это делает цикл обратной связи самым
дорогим местом проекта.

Проверено на этой машине: Roslyn из установленного .NET SDK можно запустить против
сборок игры, и он воспроизводит условия внутриигровой компиляции (C# 7.3, .NET Framework
4.x, `-nostdlib+`). Без ссылки на `netstandard.dll` при этом возникает около сотни ложных
ошибок вида «The type 'Object' is defined in an assembly that is not referenced».

Второй класс проблем — механический: нарушение слоёв, `async/await`, `MyLog` напрямую,
незащищённый вход из игрового цикла, аллокации в `Draw`. Их находит человек, но находит
нестабильно.

## Decision

Два шлюза, оба обязательные:

1. **`tools/verify-compile.ps1`** — компиляция против реальных сборок игры. Печатает
   `COMPILE OK` или список ошибок. Это доказательство вызываемости, не поведения.
2. **`tools/review-check.ps1`** — статические правила R001–R010 с уровнями
   ERROR/WARNING/INFO. Ненулевой код возврата при наличии ERROR.

Правило можно подавить комментарием `// review:allow R0NN <причина>` на той же строке.
Подавление без причины — само по себе находка (R000): иначе шлюз перестают читать.

Шлюзы не заменяют ревью и не заменяют проверку в игре. Они снимают с них механическую
часть.

## Alternatives

| Вариант | Почему отклонён |
|---|---|
| Только запуск игры | Десятки минут на цикл вместо секунд |
| Только `dotnet build` по обычному csproj | Целится не в те сборки и не в тот framework; даёт ложные зелёные результаты |
| Ручной чеклист ревьюера | Нестабилен, зависит от внимания; идеально подходит для автоматизации |

## Consequences

- Легко: ошибка компиляции и нарушение слоя находятся за секунды.
- Трудно: при смене версии игры меняются пути и набор ссылок — скрипты нужно сопровождать.
- Запрещено: сообщать о готовности изменения без зелёного `verify-compile`.
- Ограничение: `verify-compile` проверяет только то, что мод вызывает, но не то, что он
  делает.

## Verification

```powershell
pwsh -File tools/verify-compile.ps1    # → COMPILE OK — 10 file(s), 0 warning(s)
pwsh -File tools/review-check.ps1      # → REVIEW OK — no findings
```

Оба должны завершаться успешно перед сдачей изменения.

### Шлюз сам проверяется

Правило, которое никогда не срабатывало, не работает. Каждое правило проверено двумя
способами:

- **положительно** — на реальных исходниках мода даёт 0 находок;
- **отрицательно** — на специально сломанном файле даёт ожидаемую находку.

Отрицательная проверка R001–R010 выполняется так: создать временный каталог с файлом,
нарушающим ровно одно правило, и запустить
`pwsh -File tools/review-check.ps1 -SourcePath <каталог> -Rules <R0NN>`.

Эта процедура уже нашла дефект в самом шлюзе: `Get-Content` на файле из одной строки без
перевода строки возвращает скалярную строку, и `$lines[$i]` давал **символ**, а не строку —
однострочные файлы молча пропускались всеми правилами. Исправлено обёрткой
`@(Get-Content ...)`.
