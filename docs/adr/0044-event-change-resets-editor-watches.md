# 0044. Смена события event controller сбрасывает привязки, добавленные редактором

- Status: accepted
- Date: 2026-11-27

## Context

### 1. Что произошло в игре

Владелец продукта привязал к event controller грузовой контейнер (колокольчик → клик по
карточке), затем **сбросил тип отслеживаемого события** в ванильном терминале. Игра сбросила
свой список выбранных блоков. Открыв схему, владелец увидел прежнюю привязку — жёлтый порт с
именем контейнера и пунктир в его карточку.

Требование: схема не должна показывать связь, которой в контроллере больше нет.

### 2. Почему привязка пережила сброс — и почему её не видно из мира

Проверено по IL установленной сборки:

```powershell
& .\tools\dump-se-il.ps1 -Assembly 'SpaceEngineers.Game.dll' `
    -Type 'SpaceEngineers.Game.Entities.Blocks.MyEventControllerBlock' -Method 'OnSelectedEventIdChanged'
& .\tools\dump-se-il.ps1 -Assembly 'SpaceEngineers.Game.dll' `
    -Type 'SpaceEngineers.Game.Entities.Blocks.MyEventControllerBlock' -Method 'Init'
& .\tools\dump-se-il.ps1 -Assembly 'SpaceEngineers.Game.dll' `
    -Type 'SpaceEngineers.Game.Entities.Blocks.MyEventControllerBlock' -Method 'GetObjectBuilderCubeBlock'
```

`OnSelectedEventIdChanged` при переходе на **другой** компонент события вызывает
`RemoveBlocks(m_selectedBlocks.Values)` и `m_selectedBlocks.Clear()` — то есть чистит свой
список и подписку старого компонента. Ничего другого он не делает: о записях, которые мод
положил в компонент напрямую, блок не знает.

Отсюда три факта, которые вместе и дают дефект:

1. **Игровой список после смены события пуст**, и `GetObjectBuilderCubeBlock().SelectedBlocks`
   честно отдаёт пусто — читать из мира нечего;
2. **надстройка мода не изменилась**: привязка, добавленная колокольчиком, живёт в
   `MyModStorageComponent` контроллера (ADR-0018 §2), и игра о ней не знает;
3. **схема показывает объединение** (ADR-0018 §1), поэтому пустой игровой список плюс
   непустая надстройка дают ровно один порт — тот самый.

До этого изменения надстройка в такой ситуации ещё и **проигрывалась** в новый компонент
(ADR-0018 §3 п.5), то есть контроллер после смены события продолжал следить за контейнером.
Порт не только рисовался — за ним была живая подписка.

### 3. Почему «заметить смену в сессии» недостаточно

Прежний код сравнивал `SelectedEventId` с полем `ControllerState.WatchEventId`, которое жило
только в памяти узла. Поле начинается с нуля при каждом открытии экрана, поэтому:

- игрок закрыл редактор, сменил событие в терминале, открыл редактор — первое же обновление
  видит «событие изменилось» **на каждом** контроллере с непустой надстройкой и проигрывает
  её в новый компонент;
- игрок сменил событие при **закрытом** редакторе и сохранил мир — при загрузке
  `EventControllerKeeper` проигрывает надстройку в компонент нового события, не сравнивая
  ничего, потому что сравнивать не с чем.

То есть память экрана не может ответить на вопрос «для какого события записаны эти
привязки»: ответ должен переживать закрытие экрана и загрузку мира. Значит он должен лежать
рядом с самими привязками.

### 4. Что именно нужно хранить

`UniqueSelectionId` события — число из определения компонента
(`Content/Data/EntityComponents.sbc`, `EventCargoFilledEntityComponentDefinition` и остальные:
`<UniqueSelectionId>1..23</UniqueSelectionId>`), стабильное между сессиями и одинаковое на
клиенте и сервере. Оно уже используется как идентичность события в `EventControllerProbe`
(`SelectedEventId`), и в терминале оно же служит ключом выпадающего списка
(`FillEventsSelector`). Другого стабильного имени у события нет: `EventDisplayName` —
локализованная строка.

## Decision

### 1. Привязки редактора записываются вместе с событием, для которого сделаны

Значение в хранилище контроллера получает заголовок:

```
"e12 34 56"    событие 12, блоки 34 и 56     (текущий формат)
"34 56"        событие не записано            (значение прежних версий)
""             привязок нет
```

Заголовок — буква `e` и число: идентификатор блока буквой начинаться не может, поэтому
значение прежней версии разбирается как «список без события» и **не теряет ни одного id**.
Пустой список заголовка не получает: у пустого списка нет владельца, а «событие неизвестно»
не стоит записывать.

Формат живёт в `NodeStateFormat` (`FormatWatchState` / `ParseWatchState`), как и формат
позиции: это единственный слой, который проверяется без запуска игры.

### 2. Смена события — это сброс, а не повод проиграть заново

Если записанное событие и текущее **оба известны и различаются**, список привязок редактора
удаляется: хранилище очищается, порты исчезают на том же обновлении, ничего не
проигрывается. Это делает `EventControllerProbe.ReadOverlay` — единственное место, где
принимается решение, — и через него проходят оба пути: обновление схемы
(`GridGraphBuilder.RefreshControllerState`) и восстановление после загрузки мира
(`EventControllerKeeper.TryApply`). Поэтому картинка и живой блок не могут разойтись: список,
который считается мёртвым, не попадает ни в граф, ни в компонент.

`ReapplyWatchList` повторяет ту же проверку на своей границе записи: подписка блока под
событием, для которого его не добавляли, — ровно тот дефект, который это решение убирает, и
второй вызывающий не должен иметь возможности его вернуть.

**Добавление привязки читает список тем же путём.** `TryAddWatch` берёт надстройку не сырым
чтением хранилища, а через `ReadOverlay`: иначе запись, сделанная сразу после смены события
(схема ещё не успела обновиться), дописала бы новый id к старому списку и сохранила его под
новым идентификатором события — то есть усыновила бы ровно те записи, которые правило обязано
выбросить.

**Удаление — тоже через `ReadOverlay`,** и это не симметрия ради симметрии. Список может
принадлежать прежнему событию, а `Unsubscribe` работает с **текущим** компонентом: снятие
последней записи такого списка очистило бы хранилище, не сняв подписку со старого компонента, —
и снять её стало бы нечем, потому что id были бы уже потеряны. Поэтому удаление сначала
применяет правило (сбрасывает чужой список целиком, вместе с подпиской) и только потом снимает
свой id с оставшегося списка, сохраняя его событие.

### 3. Ноль — это «неизвестно», а не «другое событие»

Сравнение срабатывает только когда известны **оба** числа. `0` приходит из двух мест, и оба
означают «пока не знаю»: значение прежней версии (заголовка нет) и блок, у которого компонент
события ещё не прикреплён. Считать любой из этих случаев сменой события значило бы стирать
список игрока по отсутствию данных.

Поэтому:

- значение без заголовка **не удаляется**, а помечается текущим событием при первом же
  обновлении на сервере. Это то же допущение, которое прежний код делал на каждом
  обновлении («проигрываем в текущее событие»), но теперь оно записывается один раз, и
  следующая смена события уже сбрасывает список;
- `SelectedEventId == 0` (компонент не прикреплён, событие не прочитано) не сбрасывает
  ничего и не пишется.

**Пометка — это политика для значения, у которого владельца нет, а не лицензия писать такие
значения.** Заголовок пишется всегда, когда событие известно: в том числе при первой привязке к
контроллеру, у которого ещё нет хранилища — там `ReadOverlay` возвращает 0 просто потому, что
читать было нечего, и `TryAddWatch` спрашивает событие у блока. Иначе мод сам производил бы
«значение прежней версии» и на следующем обновлении усыновлял бы его. Единственный путь, где
непустое значение сохраняется без заголовка, — обратная запись уже-безголового значения, когда
живое событие не читается (`SelectedEventId == 0`): это сохранение статус-кво, а не выдуманный
владелец.

### 4. Сброс отписывает блок, а не только стирает запись

Удалить привязку из хранилища мало: компонент, в который её записали, после смены события
**остаётся живым и подписанным**. Проверено по IL:

```powershell
& .\tools\dump-se-il.ps1 -Assembly 'SpaceEngineers.Game.dll' `
    -Type 'SpaceEngineers.Game.Entities.Blocks.MyEventControllerBlock' -Method 'OnSelectedEventIdChanged'
& .\tools\dump-se-il.ps1 -Assembly 'SpaceEngineers.Game.dll' `
    -Type 'SpaceEngineers.Game.EntityComponents.Blocks.Events.MyEventCargoFilledEntityComponent' `
    -Method 'RemoveBlock,TriggerAction'
```

`OnSelectedEventIdChanged` снимает подписки **только для `m_selectedBlocks.Values`** — то есть
для ванильного выбора. Записи мода лежат в словаре компонента, и в `m_selectedBlocks` их нет,
поэтому старый компонент сохраняет и `m_observedBlocks`, и подписку на инвентарь. Его
`OnVolumeChanged` → `TriggerAction` → `IMyEventControllerBlock.TriggerAction` не проверяет
`IsSelected` и не сверяется с выбранным событием, так что контроллер продолжал бы запускать
тулбар по старому условию — уже без порта на схеме.

Компонент, который больше не выбран, недоступен: `IMyEventControllerBlock.SelectedEvent` отдаёт
только текущий, а перебрать компоненты блока публичного API нет. Поэтому мод **запоминает
компонент** и id блоков, которые в него подписаны (`Subscription`: `Component` + `Ids`;
заполняется в `Subscribe` и `ReapplyWatchList`), и при сбросе вызывает на нём
`RemoveBlocks(старый список)`. Это единственный способ снять подписку, которую сам мод и создал.

**Id берутся из памяти, а не из хранилища.** К моменту сброса список в хранилище может быть уже
пуст — игрок снял последнюю привязку кнопкой «x», а событие сменил после этого. Читать id из
пустого значения значило бы оставить подписку, которую больше нечем снять: снятие последней
записи «чужого» списка очищает хранилище, не отписав блок. Поэтому и удаление, и опрос берут
список блоков из `Subscription`.

Проверку делает опрос `EventControllerKeeper.Update` раз в секунду
(`EventControllerProbe.PollStaleSubscriptions`): смену события замечает не только открытая схема,
но и сессия. Сначала опрос спрашивает у запомненного компонента его `UniqueSelectionId` и сверяет
с текущим — два чтения поля, без обращения к хранилищу, — и только при расхождении отдаёт список
в `DropStaleWatchList`, где решение принимается один раз. Карта — игровые объекты, поэтому
очищается в `Uninstall` (иначе повторилась бы утечка R-002), а записи о блоках, которых больше
нет, выбывают на очередном опросе.

### 5. Память экрана больше не участвует

`ControllerState.WatchEventId` **удалён**. Вопрос «для какого события записан список»
отвечает хранилище, а не узел: узел живёт до закрытия экрана, а ответ нужен после загрузки
мира. Второе поле с тем же смыслом означало бы два источника истины, которые расходятся
ровно в тот момент, когда игрок меняет событие при закрытом редакторе.

### 6. Запрещено

- проигрывать надстройку при смене события (отменённый §3 п.5 ADR-0018);
- удалять надстройку, не зная текущего события (`SelectedEventId == 0`), или удалять
  значение без заголовка;
- стирать запись, не сняв подписку со старого компонента: порт исчезнет, а контроллер
  продолжит запускать тулбар;
- хранить идентификатор события отдельным ключом хранилища: список и его событие — один факт,
  и две записи могут разойтись, если вторая не удалась;
- сравнивать события по `EventDisplayName`: это локализованная строка, а не идентичность.

## Alternatives

| Вариант | Почему отклонён |
|---|---|
| Оставить проигрывание (ADR-0018 §3 п.5) | Это и есть дефект: контроллер продолжает следить за блоком, который игрок только что снял, а схема рисует живую привязку |
| Скрывать привязки, но хранить их (вернуть при возврате события) | Выбрано не было: порт, которого нет на схеме, нельзя удалить («x» — единственный способ), и схема перестаёт следовать за игрой, которая свой список уже выбросила |
| Оставлять только блоки, которые новое событие принимает | Привязка, которую игрок снял сменой события, осталась бы живой — просто отфильтрованной. Это тот же дефект в меньшем масштабе |
| Стирать только хранилище, не снимая подписку | Схема перестала бы показывать привязку, а контроллер продолжал бы срабатывать от снятого блока — та же ложь, только в другую сторону |
| Искать старый компонент перебором компонентов блока | Публичного API перебора у блока нет (`MyEntity.Components` вне вайтлиста), а `SelectedEvent` отдаёт только текущий |
| Сравнивать событие только в памяти узла (`WatchEventId`) | Не видит смену при закрытом редакторе и при загрузке мира (§3 Context); ровно этот случай и был в игре |
| Сравнивать событие по `EventDisplayName` | Локализованная строка: смена языка игры выглядела бы как смена события и стирала бы список |
| Отдельный ключ хранилища под идентификатор события | Две записи не атомарны: список, записанный без события, нельзя отличить от списка прежней версии, и он бы проигрывался под чужим событием |
| Удалять надстройку при каждой загрузке мира | Стирало бы список игрока при обычном сохранении/загрузке, где событие не менялось |
| Писать `SelectedBlocks` напрямую (переинициализация блока) | Отвергнуто в ADR-0018 §1d: цена — целостность блока игрока |

## Consequences

Легко:

- схема больше не показывает привязку, которой в контроллере нет: сброс события в терминале
  виден на ближайшем обновлении, даже если редактор в этот момент был закрыт;
- контроллер действительно перестаёт срабатывать от снятого блока — сброс снимает подписку, а
  не только запись;
- ответ «для какого события записан список» переживает загрузку мира, поэтому
  `EventControllerKeeper` больше не воскрешает снятую привязку;
- решение принимается в одном месте (`ReadOverlay`), а формат и правило проверяются офлайн.

Трудно:

- **привязки редактора теряются при смене события — безвозвратно.** Это цена выбранного
  правила: игра свой список в этой ситуации тоже выбрасывает, и симметричное поведение
  честнее «скрытого» списка, который нельзя ни увидеть, ни удалить;
- **значение прежней версии не сбрасывается до первой смены события после обновления.** Какое
  событие было у списка, записанного версией без заголовка, неизвестно, и угадывать в сторону
  удаления — значит стереть привязки всем, кто обновился. Первое обновление помечает список
  текущим событием; со следующей смены события правило работает;
- **запись в хранилище происходит на обновлении схемы или на опросе подписок** (пометка
  значения прежней версии, очистка сброшенного списка) — только на сервере, как и все
  остальные записи контроллера;
- **мод держит ссылку на компонент события** — единственный способ снять подписку, которую он
  сам создал. Ссылка живёт до конца сессии и очищается в `Uninstall`. Опрос раз в секунду
  сначала сверяет `UniqueSelectionId` запомненного компонента с текущим (два чтения поля) и
  только при расхождении читает хранилище — то есть в покое это resolve блока и два чтения поля
  на контроллер, а не разбор значения; запись из карты снимается, когда блок исчез, подписка
  снята или список опустел;
- **порядок портов после сброса** определяется игрой: остаются только игровые записи, в её
  порядке (ADR-0018 §Consequences, без изменений).

Если решение окажется неверным (например, владелец захочет возвращать привязки при возврате
события), меняется один метод — `EventControllerProbe.ReadOverlay`; формат значения и
геометрия не затрагиваются.

Офлайн-утверждения (`tests/OfflineChecks.cs`, секции «watch list format» и «watch list
reconciled with the game»):

- заголовок пишется перед id и возвращается разбором; пустой список заголовка не получает;
- значение без заголовка читается как тот же список и сообщает «событие неизвестно»;
- битый заголовок стоит заголовка, а не списка; `e-3` не считается событием;
- «e12» без id — пустой список для события 12;
- прежние свойства разбора (мусор, дубликаты, нули, лишние разделители, устойчивый круг)
  сохранены;
- `IsWatchListStale`: то же событие — не сброс; разные — сброс; ноль с любой стороны — не
  сброс; отрицательное число — не событие.

Человек в игре (без этого «работает» не считается):

1. Привязать к контроллеру грузовой контейнер колокольчиком (событие «Cargo Filled»).
2. **Закрыть редактор**, в терминале контроллера сменить событие (например, на «Block On Off»),
   открыть редактор — **порта контейнера нет**, и в логе есть строка
   `the event changed (1 -> 14), so 1 editor-added watch(es) were dropped`.
3. Сменить событие обратно на «Cargo Filled» — порт **не вернулся** (привязка сброшена, а не
   спрятана); привязать контейнер заново — порт появился, событие срабатывает.
4. **Проверить, что сброс действительно снимает подписку, а не только картинку.** С закрытым
   редактором привязать контейнер, настроить тулбар контроллера на видимое действие (например,
   включить лампу по «Cargo Filled»), наполнить контейнер — действие срабатывает. Затем с
   закрытым редактором сменить событие на «Block On Off», снова изменить наполненность —
   **действие больше не срабатывает** (до открытия схемы: сброс делает опрос подписок).
5. Привязать блок, сменить событие при закрытом редакторе, **сохранить и загрузить мир**,
   открыть редактор — порта нет, и контроллер по этому блоку не срабатывает.
6. Мир, созданный версией без заголовка (привязка редактора уже есть): открыть редактор —
   порт на месте, привязка работает; после этого сменить событие — порт исчез.
7. Привязки, выбранные в терминале (игровые), при смене события исчезают вместе с портами —
   их сбрасывает игра, схема это показывает.

Не проверено и требует игры: порядок, в котором игра отдаёт `SelectedEventId` сразу после
загрузки мира относительно прикрепления компонентов блока (`[НЕ ПРОВЕРЕНО]`, см.
[`api-event-controller.md`](../01-research/api-event-controller.md) §6) — от него зависит,
сколько попыток `EventControllerKeeper` уйдёт на первый вердикт; поведение на клиенте
мультиплеера (ожидается: сброс виден, запись не производится); не срабатывает ли снятая
подписка на клиенте, где `RemoveBlocks` не вызывается; и то, что `UniqueSelectionId` валидного
выбранного события никогда не равен 0 — на этом стоит запасное чтение при первой привязке
(по IL `UniqueSelectionId` копируется из определения, 1..23, но это рассуждение, а не запуск).
