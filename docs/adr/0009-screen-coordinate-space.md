# 0009. Экранное пространство: раскладка в клиентской области, отрисовка в safe-GUI

- Status: accepted
- Date: 2026-11-19
- Supersedes: —
- Amends: [0008](0008-mod-screen-api.md) (исправляет неверное фактическое утверждение; решение
  о стеке UI не меняется)
- Joint review: не требовалось — это не спор о решении, а исправление проверяемого факта об
  API, на котором держалось утверждение ADR-0008.

## Context

ADR-0008 записал, что `MyModScreen.Position`/`Size` — «доля клиентской области», и на этом
основании весь редактор рисует в нормализованных 0..1, считая 0..1 полным окном. **Это
утверждение было принято без проверки и оказалось неверным.**

Первый запуск в игре (лог `SpaceEngineers_20261119_103005892.log`, экран 1920×1200) показал
два дефекта, видимых игроком:

1. Редактор занимает не всё окно: по бокам полосы, содержимое выглядит как экран 4:3.
2. Название грида в шапке начинается правее правой границы панели и уходит за неё.

Оба — следствие одной ошибки в единицах координат. Проверено чтением IL установленной
сборки `1.211.017` новым инструментом `tools/dump-se-il.ps1` (он дизассемблирует метод в
читаемый IL с разрешёнными токенами; код игры при этом не исполняется).

### Что именно делает игра

`MyGuiManager.UpdateScreenSize` (`Sandbox.Graphics.dll`) считает **safe-GUI прямоугольник**:

```csharp
int safeWidth  = Math.Min(screenWidth, (int)(screenHeight * 1.3333334f)); // 4:3
int safeHeight = screenHeight;
m_safeGuiRectangle = new Rectangle(
    screenWidth / 2 - safeWidth / 2,  // центрирован по горизонтали
    0,
    safeWidth,
    safeHeight);
m_safeFullscreenRectangle = new Rectangle(0, 0, screenWidth, screenHeight); // только при useFullClientArea = true
m_safeScreenScale = screenHeight / 1080f;
```

`MyScreenSpace` и его спутники **всегда** вызывают преобразования с `useFullClientArea = false`:

| Метод | Что делает |
|---|---|
| `MyScreenSpace.NormalizedToPixels` | `GetScreenCoordinateFromNormalizedCoordinate(pos, false)` → `m_safeGuiRectangle` |
| `MyScreenSpace.NormalizedSizeToPixels` | `GetScreenSizeFromNormalizedSize(size, false)` → размеры от `m_safeGuiRectangle` |
| `MyScreenSpace.GetSafeGuiArea` | возвращает `m_safeGuiRectangle` в **пикселях** |
| `MyScreenSpace.TryGetCursorPosition` | `MyGuiManager.MouseCursorPosition`, а он посчитан через `GetNormalizedCoordinateFromScreenCoordinate` → тоже safe-GUI |
| `MyScreenSpaceSprite.Draw` | позиция и размер — safe-GUI |
| `MyScreenSpaceText.Draw` | позиция — safe-GUI |

То есть **0..1 у `MyScreenSpace*` — это не окно, а safe-GUI прямоугольник шириной
`min(W, 4H/3)`, то есть на любом мониторе шире 4:3 — 4:3 по центру.**

Для 1920×1200 это `safeWidth = min(1920, 1600) = 1600`, полосы по `(1920−1600)/2 = 160` px
с каждой стороны. Ровно то, что видно в игре.

### Вторая ошибка — единицы `Measure`

`MyScreenSpaceText.Measure` → `MyGuiManager.MeasureString` → `MyFontDefinition.MeasureStringRaw`
→ **`GetNormalizedSizeFromScreenSize`**, то есть возвращает **нормализованный** размер
(доля safe-GUI), а не пиксели. Старый код делал ещё и
`MyScreenSpace.PixelSizeToNormalized(...)` поверх — то есть делил на ширину safe-GUI второй
раз. Ширина текста уменьшалась в `safeWidth` раз (в 1600 раз), `TextRight` начинал рисовать
строку почти в точке правого выравнивания, и она уезжала за край. Лог ошибок не содержал:
измерение не падало, а возвращало бессмысленно маленькое число.

## Decision

**Раскладка редактора живёт в нормализованных координатах клиентской области** (0..1 по
ширине окна и 0..1 по высоте окна) — это то, что игрок считает «экраном». **Перевод в
пространство API делается в одном месте — `Vgs.Ui.VgsScreenDraw`.**

Из `MyScreenSpace.GetSafeGuiArea()` (пиксели) выводится аффинное преобразование
`layout → api`:

```
safe = GetSafeGuiArea()                      // X = ширина полосы слева, Y = 0
fullWidth = safe.Width + 2 * safe.X          // safe-прямоугольник центрирован (проверено)
scaleX  = fullWidth / safe.Width
offsetX = -safe.X / safe.Width
scaleY  = 1                                  // высота safe-GUI равна высоте окна (проверено)
offsetY = -safe.Y / safe.Height

apiX = layoutX * scaleX + offsetX            // позиции
apiW = layoutW * scaleX                      // размеры (без offset)
apiY = layoutY * scaleY + offsetY
```

Обратное преобразование — для курсора: `layout = (api − offset) / scale`.

Правила, которые теперь обязательны:

1. `Rect`, `Border`, `Text`, `TextCentered`, `TextRight` принимают **координаты клиентской
   области** и сами переводят их в safe-GUI.
2. `Measure` возвращает размер **в координатах клиентской области**: берётся
   `MyScreenSpaceText.Measure` (он уже нормализованный, в safe-GUI) и делится на `scaleX`
   (и `scaleY`). `PixelSizeToNormalized` к результату `Measure` не применяется никогда.
3. `TryCursor` возвращает курсор **в координатах клиентской области** (обратное
   преобразование), чтобы hit-testing совпадал с нарисованным.
4. Преобразование пересчитывается в начале каждого кадра отрисовки и каждого прохода ввода
   (`SyncScreenSpace()`); если safe-область пустая (dedicated server, GUI не инициализирован),
   преобразование — тождественное, и редактор рисуется как раньше (в 4:3), а не падает.
5. `MyModScreen` создаётся **без собственного фона** (`backgroundColor: null`): фон хоста
   тоже рисуется в safe-GUI и оставлял бы видимый 4:3-прямоугольник под содержимым. Фон
   редактора рисует сам экран — на всю клиентскую область.
6. Масштаб текста не меняется: `m_safeScreenScale = H/1080`, а высота safe-GUI равна высоте
   окна, поэтому `scale` имеет прежний смысл.

## Alternatives

| Вариант | Почему отклонён |
|---|---|
| Рисовать в пикселях (`MyScreenSpaceSprite.DrawPixels`, `MyScreenSpaceText.DrawPixels`, `MeasurePixels`) | Камера, зум, раскладка узлов и hit-testing уже в нормализованных единицах; вторая система единиц удваивает число мест, где прячется ошибка. Плюс `DrawPixels` внутри всё равно переводит пиксели в safe-GUI и обратно |
| Увеличить `MyModScreen.Size` (например, `(W/S, 1)`) | Не помогает: содержимое `OnDraw` рисуется в пространстве API, а не в прямоугольнике экрана-хоста. Растянулся бы только фон хоста |
| Смириться с 4:3 и рисовать в нём | Прямо противоречит требованию «редактор на весь экран»; на 21:9 полосы были бы больше трети ширины |
| Считать полосы из `MyAPIGateway.Session.Config.ScreenWidth/Height` | Такого источника в вайтлисте нет; `GetSafeGuiArea` — проверенный и уже разрешённый путь |
| Оставить `Measure` как было и «подогнать» множитель | Магическая константа, зависящая от разрешения. Ошибка была в единицах, а не в коэффициенте |

## Consequences

Стало легко:

- редактор занимает всё окно на любом соотношении сторон, включая 16:10, 21:9 и 4:3;
- раскладка (шапка, нижняя панель, кнопка «Закрыть», карточки) остаётся в привычных 0..1 и
  не зависит от разрешения;
- правое выравнивание текста наконец совпадает с отрисовкой: `Measure` и `Draw` идут через
  один и тот же API и одни и те же единицы.

Стало трудно, и это надо помнить:

- преобразование — кэш в статическом поле `VgsScreenDraw`; его обязан обновлять каждый кадр
  тот, кто рисует и читает ввод (`VgsEditorScreen.OnDraw`/`OnHandleInput`). Забыли — редактор
  деградирует до 4:3, но не падает; кэш сбрасывается в `Release()`;
- любой новый примитив в `VgsScreenDraw` обязан проходить через то же преобразование; прямое
  использование `MyScreenSpace*` в обход `VgsScreenDraw` — дефект;
- `GetSafeGuiArea()` вызывается дважды за кадр (отрисовка и ввод), а не на каждый примитив —
  поэтому преобразование нельзя «оптимизировать», вынеся его из `SyncScreenSpace`.

Запрещено:

- трактовать 0..1 `MyScreenSpace*` как клиентскую область;
- применять `MyScreenSpace.PixelSizeToNormalized` к результату `MyScreenSpaceText.Measure`;
- рисовать фон экрана средствами `MyModScreen.BackgroundColor` (он в safe-GUI).

Известные ограничения:

- **Трёхмониторный режим.** `safeGuiRectangle` в нём считается так же, как в обычном, поэтому
  формула даёт полную ширину трёх мониторов и редактор растянется на все три. Принято
  осознанно: проверить не на чем, а одномониторный случай — основной. Разбор —
  [api-screen-space.md](../01-research/api-screen-space.md) §5;
- **Пиксельная асимметрия.** `GetSafeGuiArea().Width` на 1 px больше «настоящей» safe-ширины
  (движок умножает размеры на `Width + 1`, а координаты на `Width`), поэтому правый край
  выступает примерно на 1 px за окно и обрезается вьюпортом. Субпиксельно для текста,
  безвредно для заливки; формулу ради этого не усложняем.

Если решение окажется неверным (например, Keen изменит смысл `GetSafeGuiArea`), откат —
тождественное преобразование в одном методе: остальной код не меняется.

## Verification

Статически:

```powershell
pwsh -File tools/verify-compile.ps1     # COMPILE OK
pwsh -File tools/check-whitelist.ps1    # WHITELIST OK (GetSafeGuiArea разрешён)
pwsh -File tools/review-check.ps1       # без находок
pwsh -File tools/dump-se-il.ps1 -Assembly 'Sandbox.Graphics.dll' `
    -Type 'Sandbox.Graphics.MyGuiManager' -Method 'UpdateScreenSize'   # воспроизводит safe-GUI
```

В игре (проверяет человек, экран 1920×1200 — тот же, на котором дефект воспроизводился):

1. Открыть редактор из терминала кокпита: тёмная панель занимает **всё** окно, по бокам нет
   полос; шапка и нижняя панель идут от края до края.
2. Название грида справа в шапке заканчивается внутри панели, а не за её границей. Проверить
   и с длинным именем (30+ символов): правый край внутри шапки, левый не наезжает на заголовок
   «Grid setup» (эллипсиса в коде нет — если наезжает, это отдельная задача).
3. Кнопка «Закрыть» — в правом нижнем углу **окна**, а не 4:3-области.
4. Курсор попадает туда, куда показывает: нажать «Закрыть» у самого правого края; выделить
   карточку у левого края и перетащить её — карточка следует за курсором.
5. Сменить разрешение, **не закрывая** редактор: раскладка перестраивается в следующем кадре,
   полосы не появляются. (Тест «переоткрыть редактор» прошёл бы и при пересчёте только в
   `OnOpened`, то есть не проверял бы главное свойство решения.)
6. Окно 4:3 или уже 4:3 (например 1280×1024 в оконном режиме): редактор занимает всю
   клиентскую область без растяжения и сжатия — это ветка тождественного преобразования.
