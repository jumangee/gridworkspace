# 0011. Связь — это элемент в тулбаре блока

- Status: accepted
- Date: 2026-11-20
- Supersedes: —
- Amends: [0002](0002-port-model.md) — состав выходных портов теперь определяется
  тулбаром блока, а не только курируемой таблицей; [0010](0010-port-presentation-and-binding.md)
  — «+» становится парой «T»/«F» у блоков с двумя группами срабатывания
- Joint review: не требовалось — требование («связь должна реально появляться в тулбаре
  исходного блока», «не опираться на данные вместо интерфейсов») пришло от владельца
  продукта. Факты API проверены до решения, см. §Verification.

## Context

До этого решения редактор держал связи **у себя**: `GridGraph` помнил, что «таймер №1
дёргает лампу №2 действием `OnOff`», и ничего не писал в мир. Это давало красивую картинку
и ничего больше:

- связь не работала в игре — блоки о ней не знали;
- связь не переживала перезагрузку;
- игрок не мог увидеть или поправить её в ванильном терминале;
- вычислитель (этап 3) должен был бы сам обходить граф каждый тик и вызывать
  `ITerminalAction.Apply` — то есть заново реализовывать то, что игра уже умеет, и работать
  только пока сессия жива и мод загружен.

Вторая половина проблемы — вопрос «какой блок вообще может управлять другими». Ответа в
виде флага нет: `ShowInToolbarConfig` отвечает на обратный вопрос (можно ли управлять
**этим** блоком). Курируемая таблица подтипов была бы догадкой и разошлась бы с игрой при
первом обновлении.

Третья — форма тулбара. У таймера один список действий, у сенсора и event controller два:
«да» и «нет». Это не оформление, а разные списки, которые игра активирует по разным
событиям. Один порт на событие у такого блока означал бы, что половина связей не имеет
места, куда лечь.

## Decision

### 1. Тулбар блока — единственное хранилище связи

Создание связи `источник → получатель, действие` состоит из двух шагов, и первый —
обязательный:

1. в тулбар **исходного блока** записывается элемент «блок-получатель, действие» — тот
   самый, который игрок мог бы положить руками в ванильном терминале;
2. в `GridGraph` добавляется ребро, которое помнит **ячейку** тулбара, занятую этим
   элементом (`Edge.Cell`).

Порядок именно такой: граф — отражение тулбара, а не наоборот. Если игра отказалась
принять элемент, ребро не создаётся и пользователь видит причину. Если ребро не удалось
создать после записи (например, получатель исчез между двумя вызовами), ячейка очищается.

Следствия, которые и были целью:

- связь работает без запущенного вычислителя: её исполняет сама игра;
- связь сохраняется вместе с блоком (`MyTimerBlock.GetObjectBuilderCubeBlock` кладёт
  `Toolbar.GetObjectBuilder()` в object builder);
- игрок видит и правит её в ванильном терминале;
- при открытии редактора граф **восстанавливается из тулбаров** (`GridGraphBuilder.Refresh`
  → `ReconcileToolbarEdges`), а не из собственного файла сохранения. Ручная правка в
  терминале видна редактору: элемент удалён — линия исчезла, элемент добавлен — линия
  появилась.

### 2. «Может управлять другими» определяется интерфейсом, а не таблицей

Блок является источником тогда и только тогда, когда у его сущности есть компонент,
реализующий `VRage.Game.ModAPI.IMyToolbarProvider`, **и** его тулбар имеет
`IMyToolbar.Type == MyToolbarType.ButtonPanel`, то есть активируется собственной логикой
блока. `Vgs.Game.ToolbarProbe` находит компонент перебором контейнера **по интерфейсу** (не
по имени класса — переименование в новой версии игры ничего не сломает) и читает
`ToolbarCount`, `GetToolbar(i)`, `Type`, `SlotCount` и `PageCount` у живого блока, складывая
это в `Vgs.Model.ToolbarLayout`.

Почему `ButtonPanel`: у кокпита три тулбара, и два из них (`Ship`/`LargeCockpit` и
`BuildCockpit`) — это панели игрока: первая срабатывает по нажатию клавиши, вторая строит
блоки. Событие, положенное в такую панель, не сработает по событию. Тулбар, который блок
активирует сам (таймер, сенсор, event controller, «при блокировке» у кокпита), игра создаёт
как `ButtonPanel` — это и есть проверяемый признак.

Таблица подтипов остаётся только для **имён событий** (`BlockPortCatalog`), потому что API
не умеет перечислять события. Блок с тулбаром, которого нет в таблице, всё равно становится
источником с общим событием `Triggered`: интерфейс важнее таблицы.

### 3. Группа срабатывания — часть порта, а не режим экрана

`ToolbarLayout.YesNo` означает, что у блока два независимых списка. Признак складывается из
трёх условий самой игры: `MyToolbar.YesNoBackground` (игра копирует его из
`MyCubeBlockDefinition.YesNoToolbarBackground`, то есть это заявление самого определения
блока), `MyToolbar.CanShowYesNoBackgrounds` (в конструкторе `true`; `MyShipController.Init` —
единственный писатель — сбрасывает его ручному и строительному тулбарам) и `SlotCount == 2`.
Ровно эту тройку проверяет ванильный `MyGuiControlToolbar.SetGridItemAt`, прежде чем нарисовать
иконки true/false. Двухслотовый тулбар без флага определения — обычный тулбар, раздваивать его
нельзя.

Через ModAPI видны только `Type` и `SlotCount`: флага `YesNoBackground` в `IMyToolbar` нет.
Поэтому мод читает его **из определения блока** — `MyCubeBlockDefinition.YesNoToolbarBackground`
через `IMyCubeBlock.SlimBlock.BlockDefinition`. Это первоисточник, а не обход: `MyToolbar.Init`
копирует ровно это поле. Условие `CanShowYesNoBackgrounds` для любого `ButtonPanel`-тулбара
истинно, потому что `false` ставится только ручному и строительному тулбарам кокпита, а они
отсеяны проверкой `Type`. Поэтому:

- каждый выходной порт такого блока раздваивается: `Detected#true` и `Detected#false`
  (`PortGroup.Yes` / `PortGroup.No`);
- ключ порта содержит группу, потому что связь хранится по ключу и должна помнить, в какой
  из двух списков она легла;
- на карточке вместо одной кнопки «+» рисуются две — «T» и «F» (`PortGeometry.TryBindButton`);
  нажатие выбирает группу **до** выбора получателя, и выбранный порт запоминается в
  состоянии привязки (`_bindPort`), а не пересчитывается позже;
- порт группы «да» пишется только в слот 0 страницы, «нет» — только в слот 1. Игра
  активирует слот 0 на «вошёл» и слот 1 на «вышел» (`MySensorBlock.OnFirstEnter` /
  `OnLastLeave`), поэтому элемент в чужом слоте сработал бы не по тому событию.

### 4. Одно действие на страницу; повтор — на следующую страницу

Ванильный экран настройки тулбара, бросая элемент в ячейку, сначала удаляет все остальные
ячейки **текущей страницы** с таким же элементом. Значит дубликат, положенный рядом, игра
сама сотрёт при первой правке страницы. Правило редактора (`Vgs.Model.ToolbarPlanner`):

1. страницы перебираются по порядку; берётся первая, где нужный слот свободен и это
   действие ещё не стоит;
2. если действие стоит на всех страницах — связь **невозможна**, и пользователь получает
   сообщение, а не тихую перезапись;
3. если свободных ячеек нужного слота нет вообще — другое сообщение.

То есть у таймера (10 страниц) одно и то же действие на одном блоке можно повесить 10 раз;
одиннадцатый раз — отказ. Это и есть то ограничение, о котором просил владелец продукта.

### 5. Запись — только через ModAPI: `BeginChanges()` → `Set` → `Apply()`

Запись идёт через `IMyToolbarSlots.BeginChanges()` и `IMyToolbarChangeBuilder`:

```csharp
IMyToolbarChangeBuilder change = toolbar.BeginChanges();
change.Set(index, MyToolbarItemInfo.BlockAction(target.EntityId, actionId));
bool ok = change.Apply();
```

Это единственный разрешённый путь. `MyToolbar.SetItemAtIndex` делает то же самое и был первым
выбором, но `MyToolbar` и `MyToolbarItemFactory` лежат в `Sandbox.Game.Screens.Helpers`,
которое вайтлист IL-скриптов **не разрешает**: `Sandbox.Game` разрешён точно, а подпространства
— нет. Первая версия мода на этом и упала: локальная компиляция проходила, игра отклоняла
загрузку с «The type or member 'MyToolbar' is prohibited». Подробности —
[`api-toolbar.md` §0](../01-research/api-toolbar.md).

`Apply()` возвращает `bool` и не бросает. Внутри — `MyToolbar.SendChanges`, который отклоняет
пачку, если `IsOwnedHere == false`; для тулбара блока это `Sync.IsServer`, то есть **в
одиночной игре и на хосте запись работает, на удалённом клиенте мультиплеера — нет** (тулбар
блока принадлежит серверу). Отказ превращается в `WriteResult.Rejected` с сообщением
пользователю, а не в мнимую связь.

Элемент валидирует сама игра: `MyToolbarChangeBuilder.Build` для `BlockAction` создаёт object
builder и через `Fill` кладёт `_Action`; если действие не найдено, `Build` вернёт `null`, `Set`
пометит пачку `m_rejected`, `Apply()` вернёт `false`. После записи ячейка **читается обратно**
(`TryGetItem`): если в ней не тот блок или не то действие, ячейка очищается и связь считается
неудавшейся. «Игра не приняла» — штатный исход, а не исключение.

## Consequences

Что становится проще:

- вычислитель (этап 3) больше не нужен для базовой работы связей: игра исполняет их сама.
  Остаётся то, чего игра не умеет, — условия, значения, задержки;
- сохранение и мультиплеер приходят бесплатно: тулбар синхронизируется игрой;
- редактор и терминал перестают быть двумя несовместимыми представлениями одной схемы.

Чем платим:

- **предел ёмкости стал видимым**: 90 ячеек у таймера — это не «сколько угодно», и
  пользователь должен понимать, почему одиннадцатая связь не встала;
- `MyToolbar`, `MyToolbarItemFactory`, `MyToolbarItemTerminalBlock` и `MyToolbarType` — не
  «чистый» mod-API, а игровые типы. Первые три моду **запрещены**, поэтому мод обращается
  только к `VRage.Game.ModAPI`; `MyToolbarType` разрешён, но привязан к версии игры:
  `check-whitelist.ps1` (с `-SelfTest`) и `verify-compile.ps1` обязательны при каждом
  изменении;
- запись требует **прав на тулбар**: на удалённом клиенте мультиплеера `Apply()` возвращает
  `false`. Это ограничение игры, а не мода; пользователь получает сообщение, а не молчание;
- запись требует **живого блока**. Экран не может показать связь, которую нельзя записать,
  поэтому «мертвый» узел (блок уничтожен) отвергается с сообщением;
- граф обязан сверяться с тулбаром на каждом обновлении. Это чтение `ItemCount` ячеек на
  блок с бюджетом `VgsConstants.MaxToolbarCellsScanned`.

Отвергнутые альтернативы:

| Альтернатива | Почему нет |
|---|---|
| Свой вычислитель вместо тулбара | Дублирует механику игры, работает только при загруженном моде, не сохраняется |
| Таблица «подтип → может управлять» | Догадка; ломается на блоках других модов и при обновлении игры |
| `ShowInToolbarConfig` как признак источника | Отвечает на обратный вопрос (можно ли управлять этим блоком) |
| `MyToolbar.SetItemAtIndex` | Тип в `Sandbox.Game.Screens.Helpers` — запрещён мод-скрипту; мод не загружается |
| `MyToolbar` / `IMyToolbarOwner` напрямую | То же: вайтлист разрешает `Sandbox.Game` точно, без подпространств |
| Своя таблица вайтлиста в шлюзе | Разошлась с игрой один раз и стоила запуска игры; теперь шлюз читает IL игры и проверяет себя |
| Один порт на событие у yes/no блока | Половина связей не имеет ячейки; элемент попал бы в чужой список |
| Хранить связи в своём файле | Терминал и редактор разошлись бы; связь не работала бы без мода |

## Verification

Проверено на этой машине (2026-11-20, перепроверено 2026-11-21), команды и результаты — в
[`docs/01-research/api-toolbar.md`](../01-research/api-toolbar.md):

  `IMyToolbarSlots`, `IMyToolbarChangeBuilder`, `MyToolbarItemInfo`, `MyToolbarItemKind`,

- `tools/check-whitelist.ps1 -Dump` — вайтлист, декодированный из IL игры: `Sandbox.Game`

- `tools/dump-se-il.ps1` по `MyToolbar..ctor` и `MyToolbar.Init` (флаг «да/нет» приходит из

  `MyGuiControlToolbar.SetGridItemAt` (та же тройка условий),
  `MySensorBlock.OnFirstEnter/OnLastLeave` (слоты 0 и 1),
  `MyEventControllerBlock.TriggerAction` (шаг 2), `MyToolbar.ActivateAllItemsAtSlot`,
  `MyGuiScreenToolbarConfigBase.DropGridItemToToolbar`, `MyTimerBlock.UpdateOnceBeforeFrame` —
  слоты групп и правило «одно действие на страницу»;
- `tools/dump-se-il.ps1` по `MyTimerBlock.Init`, `MySensorBlock.Init`,
  `MyEventControllerBlock.Init` — каждый создаёт `MyToolbar(ButtonPanel, …)` и добавляет
  `MyToolbarProviderComponent`; по `MyToolbar.SendChanges` и `get_IsOwnedHere` — условие
  записи; по `MyToolbarChangeBuilder.Build` — валидация элемента;
- `tools/read-se-whitelist.ps1` + `tools/check-whitelist.ps1` — все используемые типы
  разрешены мод-скрипту;
- `tools/offline-check.ps1` — правила размещения (`ToolbarPlanner`), геометрия кнопок
  «T»/«F», инварианты ячеек в `GridGraph`.

Не проверено и требует человека в игре: что элемент, записанный модом, действительно
срабатывает; что событие сенсора «нет» активирует слот 1 (по коду — да, в игре — нет);
что запись видна второму игроку в мультиплеере. Список приёмки — в
[`docs/ROADMAP.md`](../ROADMAP.md).
