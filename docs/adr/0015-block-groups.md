## Context

### 1. Что просили

На схеме должны быть видны **группы блоков** — те самые именованные группы, которые игрок
создаёт в терминале. Группа рисуется светло-серым фоном. У группы особое правило видимости:
она видна, если виден **хотя бы один** её блок. У группы не может быть исходящих портов, но
могут быть входящие, и набор действий у неё — не «как у блока».

Последний пункт в требовании был помечен как догадка («я могу ошибаться»), поэтому первым
делом проверено, **что игра на самом деле делает с группой**. Результат — в
[`docs/01-research/api-block-groups.md`](../01-research/api-block-groups.md); ниже только то,
что из него следует.

### 2. Что игра делает на самом деле (проверено)

[ПРОВЕРЕНО] `tools/dump-se-il.ps1 -Type 'Sandbox.Game.Screens.Helpers.MyToolbarItemTerminalGroup'
-Method 'GetActions'`, `-Method 'GetValidActions'`,
`-Method '<GetValidActions>g__CollectValidActions|13_0'`:

```
типы = множество GetType() всех блоков группы
если тип один                → действия этого типа, включённые хотя бы у одного участника
иначе если не все блоки — MyFunctionalBlock → действий НЕТ
иначе                        → пересечение по Id действий типов всех блоков,
                               включённых у КАЖДОГО участника
```

Четыре следствия, и три из них противоречат разумной на вид догадке:

- **«Самый общий предок» не ищется.** Гипотеза из требования неверна: игра берёт действия
  *типа* блока и при разных типах оставляет **пересечение по id**. Предок всплывает только при
  исполнении, где действие применяется к блоку, чей тип наследует тип регистрации.
- **Смешанная группа с не-функциональным блоком не имеет действий вообще** — один конвейер
  рядом с таймером, и группа перестаёт предлагать что-либо.
- **Фильтр `IsEnabled` несимметричен**: в однотипной ветви он означает «включено хотя бы у
  одного», в смешанной — «у каждого», потому что игра передаёт туда либо все блоки, либо по
  одному. Свести его к одному правилу значило бы разойтись с игрой в одну из сторон.
- **`IsValidForGroups`** — часть того же фильтра, но моду недоступна; проверено, что игра её
  нигде не выключает (см. §3.1 исследования).

[ПРОВЕРЕНО] `-Method 'Activate'`: при срабатывании действие применяется к **каждому
функциональному** блоку группы, у которого оно есть. Одна связь — много блоков.

[ПРОВЕРЕНО] `dump-se-api.ps1 -Types 'VRage.Game.ModAPI.MyToolbarItemInfo','VRage.Game.ModAPI.MyToolbarItemKind'`:
у игры есть отдельный вид элемента тулбара `GroupAction(blockEntityId, groupName, actionId)`, и
`dump-se-il.ps1 -Type 'Sandbox.ModAPI.MyToolbarApiExtensions' -Method 'GroupAction'` показывает,
что официальный путь пишет туда **блок-контекст**, а не блок группы.

[ПРОВЕРЕНО] `IsValidForGroups` — член внутреннего `Sandbox.Game.Gui.ITerminalAction`, моду
недоступен; по умолчанию `true` (`-Method '.ctor'`), и **ни один метод игры его не выключает**
(скан IL `Sandbox.Game.dll` + `SpaceEngineers.Game.dll`: 0 совпадений; контрольный прогон того
же сканера по `set_Visible` — 312).

### 3. Группа — не сущность

У группы нет `EntityId`: её адресует **имя** (`MyToolbarItemInfo.GroupAction` хранит имя,
`MyBlockGroup.GetBlocks` ищет группу по имени). Значит:

- переименование группы — это **другая** группа, и связи, которые на неё ссылались, перестают
  разрешаться. Это поведение игры, а не наше упрощение;
- позиция рамки не может храниться на группе (негде) — она выводится из позиций карточек
  участников и потому не сохраняется.

### 4. Почему рамка, а не карточка

Карточка — метка блока: имя, подтип, «+» ([ADR-0010](0010-port-presentation-and-binding.md)).
У группы нет ни подтипа, ни тулбара, ни «+». Нарисовать её карточкой значило бы соврать дважды:
что у неё есть тип и что она может быть источником. Поэтому группа — **рамка позади карточек
участников**, с полосой имени по верхней грани.

## Decision

### 1. Группа — узел второго вида, `NodeKind.Group`

`Node` получает `Kind`, `GroupName`, `Members` и `FrameSize`; блок — по-прежнему `NodeKind.Block`
с `EntityId`. Группы хранятся в `GridGraph` **отдельной таблицей по имени**, а не в списке
блоков: у них нет id, и они рисуются другим проходом (позади карточек).

Общее у двух видов: входящий порт, полоса порта, попадание мышью, меню действий, ребро графа.
Различное — в одном месте каждое: `Kind`, `GroupName`, `Members`, `FrameSize`, отсутствие
тулбара и исходящих портов.

### 2. «Show in VGS» для группы агрегируется, а не дублируется

Отдельного флага у группы **нет**. `GridGraphBuilder.SyncGroups` передаёт в
`GridGraph.SyncGroup` только тех участников, которые уже попали в граф; группа без единого
такого участника **не создаётся** (а существующая — удаляется вместе со входящими рёбрами).

Отсюда ровно требуемое правило: все блоки выключены → группы нет; хотя бы один включён →
группа есть. И оно не требует нового хранилища, нового контрола и новой синхронизации: флаг
остаётся на блоке, как в [ADR-0013](0013-show-in-vgs-flag.md).

Важное следствие, которое надо понимать: **рамка рисуется вокруг видимых участников**, но
набор действий считается по **всей** группе, включая скрытые блоки и блоки подгридов. Игра
применяет действие ко всем, поэтому список, посчитанный по видимым, обещал бы меньше, чем
связь делает.

### 3. Набор действий группы — правило игры, вынесенное в модель

`BlockPortCatalog.ComputeGroupActionIds(members, into)` — чистая функция от
`GroupMemberActions` (ключ типа, признак функциональности, id действий и подмножество
включённых) и есть ровно три ветви из §2, включая несимметричный фильтр `IsEnabled`. Она
живёт в `Vgs.Model`, потому что это единственное место, где правило проверяется офлайн
(`tests/OfflineChecks.cs`), а ошибка в нём — это связь, которая молча ничего не делает.

Порты группы строятся `FillActions` только когда список id **изменился**: иначе каждый refresh
пересоздавал бы объекты `Port` и ронял выделение, наведение и открытое меню. В том же случае
удаляются рёбра на порты, которых у группы больше нет: действие выпало из пересечения — его
нельзя исполнить, и линия к нему была бы линией в никуда.

### 4. Связь «блок → группа» — элемент тулбара вида `GroupAction`

`ToolbarWriter.TryWriteGroup(source, sourceNode, port, groupName, actionId, out cell)` пишет
`MyToolbarItemInfo.GroupAction(source.EntityId, groupName, actionId)` через тот же
`BeginChanges().Set(...).Apply()` и с той же проверкой чтением обратно, что и блок-действие
([ADR-0011](0011-toolbar-is-the-connection.md)). Контекстом служит **блок-источник**: игра
находит грид по этому блоку, а источник по построению на том же конструкте и существует ровно
столько, сколько существует элемент.

Правило размещения (`ToolbarPlanner`) не меняется: группа — такой же «получатель», и
дубликатом считается то же действие на **том же** получателе (тот же блок или та же группа).
Перед записью группа **перепроверяется по имени** в терминальной системе грида и её действие
подтверждается хотя бы одним участником: имя — это идентификатор, поэтому группу могли
переименовать или распустить в окне до одного refresh (≤1.5 с), а элемент с исчезнувшим именем
игра не исполнит никогда, и чтение обратно этого не заметит — элемент хранится дословно.
Чтение и сверка (`GridGraphBuilder.SyncCells`) различают два вида по `CellContents.Kind`
(`MyToolbarItemKind` отображается на `Vgs.Model.CellKind` в `ToolbarWriter.ReadCell`),
поэтому элемент, поставленный руками в терминале, тоже превращается в линию.

### 5. У группы нет исходящих портов

`Node.CanDriveBlocks = false` в конструкторе группы, `Toolbar = ToolbarLayout.None`,
`Events` пуст. Следствия бесплатны: нет «+», нет «T»/«F», `BeginBind` не может начаться с
группы, `ToolbarWriter.TryWrite*` не примет группу источником, `GridGraph.TryConnect` не найдёт
у неё событийного порта.

### 6. Рамка выводится из карточек

`PortGeometry.TryGroupFrame` считает наименьший прямоугольник, содержащий карточки участников
**и их стаки портов**, плюс отступ и полоса имени. `PortGeometry.LayoutGroupFrames(graph)`
применяет результат через `Node.SetFrame`. Вызывается после построения графа, после каждого
refresh, после перетаскивания карточки, после переноса группы и после изменения связей —
никогда из пути отрисовки.

Рамка остаётся **производной**: её нельзя сдвинуть отдельно от участников. Но с ADR-0016
полоса имени — ручка переноса **всей** группы: жест применяет одно смещение ко всем
нарисованным участникам (`GridGraph.OffsetGroupMembers`), и рамка встаёт на новое место сама,
сохраняя размер. Запрет §6 в прежней редакции («перетаскивание группы запрещено») снят этим
решением.

Попадание мышью по группе — **полоса имени и полосы портов**, но не внутренность рамки:
внутренность принадлежит карточкам участников, а промежутки между ними — холсту (иначе
панорамирование по сгруппированному узлу было бы невозможно).

## Alternatives

| Вариант | Почему отклонён |
|---|---|
| Группа — карточка с подтипом «group» | Соврала бы дважды: у группы нет типа и нет тулбара; пришлось бы объяснять, почему у карточки нет «+» |
| Флаг видимости на группе (своё хранилище) | У группы нет сущности, а значит нет `MyModStorageComponent`; хранить пришлось бы по имени в файле мира — и «скрыть группу» разошлось бы с «скрыть её блоки» |
| Считать действия группы как **объединение** действий участников | Игра так не делает: она берёт пересечение, и элемент с несуществующим у части блоков действием не срабатывает вовсе. Объединение дало бы связи, которые молча не работают |
| Считать действия по «самому общему предку» | Игра не ищет предка: предок важен только при исполнении. Правило пересечения проверено по IL |
| Считать действия по видимым участникам | Связь исполняется для всех, включая скрытых и блоки подгридов; меню обещало бы меньше, чем делает связь |
| Один фильтр `IsEnabled` на обе ветви | Игра применяет «хотя бы у одного» в однотипной ветви и «у каждого» в смешанной; единый фильтр разошёлся бы с игрой в одну из сторон |
| Разворачивать группу в N связей «блок → каждый участник» | Это N записей в тулбаре вместо одной, N страниц на повтор и рассинхрон при изменении состава группы. Игра умеет группу сама — надо пользоваться |
| Разрешить группе быть источником | Нечем: нет тулбара, нечем «сработать». Порт, который нельзя исполнить, — обещание, которое мод не выполнит |
| Перетаскиваемая рамка с сохранённой позицией | Позиции негде хранить (нет сущности), а «рамка отдельно от участников» ломает обещание «эти блоки вместе». **Перенос группы этим не запрещается** — он реализован как смещение участников, см. [0016](0016-group-drag.md) |
| Считать «не удалось прочитать» равным «группы нет» | Группа, снятая с графа, уносит свои рёбра, и сверка их не вернёт — узел уже удалён. Один неудачный кадр стирал бы картинку навсегда, хотя тулбар хранит связь |

## Consequences

Что становится легко:

- одна связь включает/выключает целую группу — то, ради чего группы в игре и существуют;
- состав группы можно менять в терминале: после refresh рамка и набор действий сами
  подстроятся, связь останется;
- видимость группы не требует ни нового контрола, ни нового хранилища, ни новой синхронизации;
- правило действий группы проверяется офлайн, а не в игре.

Чем платим:

- **имя — идентификатор.** Переименовал группу — связь перестала разрешаться. Это поведение
  игры, но игрок увидит «линия пропала», и это надо сказать в подсказке/документации, а не
  делать вид, что связи не было;
- **правило действий неочевидно.** Смешанная группа с не-функциональным блоком (конвейер,
  броня) не предложит ничего. Это правило игры, и редактор его повторяет, а не смягчает:
  смягчить значило бы предложить действие, которое игра не исполнит;
- **`IsValidForGroups` моду недоступен.** Сегодня это ничего не меняет (игра его нигде не
  выключает — проверено сканом IL), но действие, добавленное другим модом, редактор может
  предложить, а игра — отфильтровать. Расхождение будет видно как «связь создана, но не
  срабатывает»; лечится только новым полем в ModAPI, то есть не нами;
- **бюджет чтения.** Скрытые участники и участники подгридов читаются из мира
  (`GetActions` + `IsEnabled`), поэтому на группу есть предел `MaxGroupMembersScanned`, а на
  число групп — `MaxGroupsScanned`. При исчерпании список действий группы остаётся прежним
  (лучше устаревший, чем неполный), а группа **не** снимается с графа: «не прочитано» — не
  «не существует». Непрочитанные группы перечисляются в лог одной throttled-строкой;
- **мультиплеер** наследует ограничение [ADR-0011](0011-toolbar-is-the-connection.md): запись
  в тулбар возможна только там, где `Sync.IsServer`. Чтение работает везде.

Если решение окажется неверным (например, игроки ждут группу-источник), откат дешёвый:
`NodeKind.Group` + `Node.Events` + `ToolbarProbe` для группы. Дороже станет только миграция
уже созданных связей — их элементы в тулбарах останутся, но перестанут быть видны.

Новые утверждения в `tests/OfflineChecks.cs` — ровно те, которые нельзя увидеть в игре:

пересечения), геометрия рамки и полосы порта, попадание мышью по полосе имени против
внутренности рамки.

Чего офлайн-шлюз проверить **не может** и что поэтому остаётся на человеке: сам обход
терминальной системы (`ReadGroups`/`SyncGroups`) — он живёт в `Vgs.Game`, который шлюз не
компилирует. Офлайн проверено правило, которое этот обход применяет, и модель, в которую он
пишет; связка «прочитали группы → передали только нарисованных участников» проверяется в игре
(пункты 3 и 6 ниже).

Человек в игре (без этого «работает» не считается):

1. Создать в терминале группу из двух ламп, открыть редактор → вокруг их карточек
   светло-серая рамка с именем группы; рамка не перекрывает карточки и содержит их полосы
   портов.
2. «Таймер → группа, `OnOff`»: в тулбаре таймера появился **один** элемент с именем группы;
   запуск таймера включает **обе** лампы.
3. Выключить «Show in VGS» у одной лампы → рамка осталась, вторая лампа на месте; выключить у
   второй → рамка и её линии исчезли; включить обратно → вернулись, линия в тулбаре цела.
4. Сделать группу из лампы и конвейера → меню действий группы пусто (правило игры), и это
   видно, а не «связь создана, но не работает».
5. Переименовать группу в терминале → линия исчезла после refresh (имя — идентификатор);
   вернуть имя → линия вернулась.
6. Удалить группу в терминале → рамка и её линии исчезли, элементы в тулбарах **не** тронуты.
7. Перетащить участника группы → рамка поехала за ним и пересчитала размер. Перенос всей
   группы за полосу имени — отдельное решение, [0016](0016-group-drag.md).
8. «x» на входящем порте группы → линия и элемент в тулбаре источника исчезли.
9. Группа из двух ламп, у одной из которых действие выключено (например, лампа не
   функциональна): список группы не пуст, если все блоки одного типа, и пуст, если типы
   разные — это асимметрия игры из §2, и её видно в меню.

Не проверено и требует игры: что `GroupAction`, записанный модом, действительно срабатывает
(по IL путь тот же, что у ванильного элемента, но это не запуск); поведение группы с блоками
подгридов; поведение при переименовании группы, пока редактор открыт; как выглядит рамка на
экране (светлота заливки и читаемость имени в полосе).
