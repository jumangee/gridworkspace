# Терминология

Словарь проекта. Одно слово — одно значение, и это значение одинаково в коде, в документах и
в разговоре. Если понятие живёт в коде, рядом указан тип; если это понятие экрана — метод,
который его рисует.

Документ обязателен к поддержке: новое понятие, появившееся в коде без строки здесь, —
дефект документации (как и разошедшаяся диаграмма в
[03-architecture.md](03-architecture.md)).

---

## 1. Блок и узел

| Термин | Значение | В коде |
|---|---|---|
| **блок** | Настоящий блок грида Space Engineers. Живёт в мире, может быть уничтожен, читается только из `Vgs.Game` | `IMyTerminalBlock` |
| **группа блоков** | Именованный набор терминальных блоков, который игрок создаёт в терминале. **Не сущность**: у неё нет `EntityId`, её идентификатор — имя. Может входить в группу блоков подгридов конструкта | `Sandbox.ModAPI.IMyBlockGroup` |
| **узел** | Снимок блока **или группы** на поле редактора: имя, координата на поле, список портов. Живых сущностей не содержит | `Vgs.Model.Node`, `NodeKind` |
| **карточка** | То, как узел-блок выглядит: прямоугольник с названием блока и его типом. Порт — не карточка, он под ней | `PortGeometry.CardRect` |
| **рамка группы** | То, как узел-группа выглядит: светло-серый прямоугольник **позади** карточек участников, с полосой имени по верхней грани. Не карточка: у группы нет ни подтипа, ни «+», ни тулбара. Выводится из карточек участников; за полосу имени переносится вся группа ([ADR-0016](adr/0016-group-drag.md)) | `PortGeometry.TryGroupFrame`, `Node.FrameSize` |
| **полоса имени** | Верхняя полоса рамки группы с её именем. Единственная часть рамки, попадание по которой выбирает группу: внутренность принадлежит участникам | `PortGeometry.TryGroupTitleRect` |
| **участник группы** | Блок, входящий в группу. На схеме различаются **нарисованные** участники (у них есть карточка) и **все**: рамка считается по первым, набор действий — по всем | `Node.Members` |
| **поле** | Прокручиваемая плоскость редактора, по которой раскладываются карточки. Поле бесконечно; сетка на нём — только ориентир | `DrawGrid` |
| **граф** | Все узлы одного грида (блоки и группы) и все связи между ними | `Vgs.Model.GridGraph` |
| **видимость узла** | Флаг блока «Show in VGS». Выключен — блок в граф не попадает, его карточки и линий нет; связи при этом остаются в тулбарах и работают | `NodeStateStore.IsShown` |
| **видимость группы** | Правило **агрегирования**, а не отдельный флаг: группа видна, если виден хотя бы один её участник. Все скрыты — группы нет в графе, её линий нет; связи при этом остаются в тулбарах | `GridGraph.SyncGroup`, `GridGraphBuilder.SyncGroups` |
| **сохранённая позиция** | Место карточки, записанное на самом блоке (`"x y"`), а не в таблице по `EntityId`. У группы позиции нет — рамка выводится из участников | `NodeStateStore.TryReadPosition`, `NodeStateFormat` |

Узел — не блок. Узел переживает перетаскивание и не переживает уничтожение блока; связь
между ними — `Node.EntityId`, который может устареть и перепроверяется при обновлении.

Отдельно: **позиция карточки** — свойство блока, а не узла. Узел живёт до закрытия экрана,
блок — до разрушения. Поэтому позиция хранится на блоке, и `Node.Position` — лишь её копия,
прочитанная при построении графа ([ADR-0012](adr/0012-layout-lives-on-the-block.md)).

## 2. Порты

**Порт** — одна соединяемая точка узла. Порт — это не «место на карточке» и не «линия»:
это именованная возможность блока, которую можно соединить. Порт рисуется прямоугольником
(«полосой порта») под карточкой, но существует независимо от того, нарисован ли он.

Портов два вида, и они не симметричны — эта асимметрия и есть суть модели
([ADR-0002](adr/0002-port-model.md)):

| Термин | Что это | Откуда берётся | Тип | В коде |
|---|---|---|---|---|
| **входящий порт** (вход, действие) | То, что блок можно попросить сделать: `OnOff`, `TriggerNow`, `Open` | Реальный список действий блока из игры — поэтому точен для любого блока, включая блоки других модов | `PortKind.Action` | `Node.Actions` |
| **исходящий порт** (выход, событие) | То, о чём блок сообщает тем, что запускает свой тулбар: `Triggered`, `Detected#true`, `TargetLocked` | Курируемая таблица имён: API не умеет перечислять события. Существование порта определяется тулбаром блока | `PortKind.Event` | `Node.Events` |

Общие определения:

- **ключ порта** — стабильный идентификатор (`"Triggered"`, `"OnOff"`, `"Detected#true"`).
  Связи хранятся по ключу, никогда по индексу: добавление порта в тип блока не должно
  перекоммутировать существующие графы. `Port.Key`
- **отображаемое имя** — ключ, разбитый по заглавным буквам: `TriggerNow` → `Trigger Now`.
  `Port.DisplayName`, `BlockPortCatalog.Humanize`
- **полоса порта** — прямоугольник, которым порт нарисован: примыкает к нижней грани
  карточки, **во всю её ширину**, стакается вниз вплотную к соседним. Фон полосы зависит от
  направления, **рамка — цвета карточки**: полоса принадлежит блоку и читается как часть
  карточки, а не как отдельная коробка. `PortGeometry.TryPortBarRect`
- **точка порта** (кружок) — круг **внутри** полосы: у правой границы у исходящего (отсюда
  линия уходит), у левой у входящего (сюда линия приходит). Круглый на экране при любой
  пропорции окна. `PortGeometry.TryPortDot`
- **кнопка удаления** («x») — круг **внутри** полосы, на стороне, противоположной точке:
  у исходящего порта слева, у входящего справа. Белый диск с «x» цветом фона полосы; нажатие
  удаляет **все** связи этого порта (ADR-0014). `PortGeometry.TryPortRemoveButton`,
  `VgsEditorScreen.RemovePortConnections`
- **управляющие круги порта** — точка и «x» вместе. Один размер на обе: диаметр — 75% высоты
  полосы, отступ от границы — 4 пикселя при высоте окна 1080 (по горизонтали с поправкой на
  пропорции). `VgsConstants.PortControlRadius`, `PortControlMargin`
- **стакан** — вертикальная стопка полос под одной карточкой без зазоров между ними.
  Исходящие стакаются первыми, вплотную к карточке; входящие — ниже. `PortGeometry`
- **слот** — номер полосы в стакане. `0` — ближайшая к карточке. `-1` значит «не рисовать».
  `Port.Slot`
- **подпись порта** — имя порта между двумя управляющими кругами, по центру высоты полосы;
  размер шрифта пропорционален зуму (зажима, как у текста карточки, нет). `PortGeometry.TryPortLabelRect`

### Тулбар: связь, группа, ячейка

Это словарь второй половины модели — той, которая отвечает за то, чтобы связь **работала**,
а не только рисовалась ([ADR-0011](adr/0011-toolbar-is-the-connection.md)).

| Термин | Значение | В коде |
|---|---|---|
| **тулбар** | Список действий самого блока: то, что игра запускает, когда блок срабатывает. Не путать с «панелью тулбара» кокпита — та принадлежит игроку и по событию не срабатывает | `ToolbarLayout` |
| **ячейка** | Одно место в тулбаре: страница + слот. Одна связь — одна ячейка, и две связи не могут делить ячейку | `ToolbarCell` |
| **страница** | Набор ячеек, который игра считает одной «тулбар-панелью». Действие на разных страницах — разные действия для игры | `ToolbarLayout.PageCount` |
| **группа** («да»/«нет») | Один из двух независимых списков действий блока с двумя слотами на страницу. Слот 0 — «да», слот 1 — «нет» | `PortGroup` |
| **форма тулбара** | Сколько слотов, сколько страниц, две группы или одна. Читается у живого блока, не из таблицы | `ToolbarLayout`, `Vgs.Game.ToolbarProbe` |
| **признак «может управлять»** | У сущности блока есть компонент `VRage.Game.ModAPI.IMyToolbarProvider` и его тулбар — `ButtonPanel`, то есть запускается собственной логикой блока. Не путать с `ShowInToolbarConfig` (тот про обратное) | `Node.CanDriveBlocks` |
| **правило размещения** | Куда именно кладётся элемент: свободный слот нужной группы на первой странице, где это действие ещё не стоит. Если такой страницы нет — связь невозможна. Правило само решает, что считать свободным, поэтому получает **содержимое** ячейки, а не готовый ответ | `Vgs.Model.ToolbarPlanner` |
| **содержимое ячейки** | Что лежит в ячейке: пусто, действие блока, действие группы или чужой элемент (определение блока, предмет инвентаря). Чужой элемент — **не** свободная ячейка: писать поверх него значит стирать чужую связь | `Vgs.Model.CellContents`, `CellKind` |
| **запись связи** | Единственное место, где мод меняет блок: элемент «получатель + действие» кладётся в тулбар источника и читается обратно для проверки | `Vgs.Game.ToolbarWriter` |
| **элемент группы** | Второй вид элемента тулбара: «действие на группу» (`MyToolbarItemKind.GroupAction`). Хранит **имя** группы и блок-контекст, по которому игра находит грид. При срабатывании применяет действие к каждому функциональному участнику группы | `MyToolbarItemInfo.GroupAction`, `ToolbarWriter.TryWriteGroup` |
| **перенос группы** | Перетаскивание группы за **полосу имени**: одно смещение применяется ко всем нарисованным участникам, взаимное расположение карточек сохраняется, рамка следует за ними и размер не меняет. Участник, скрытый «Show in VGS» или живущий на подгриде, не переезжает — у него нет карточки | `GridGraph.OffsetGroupMembers`, `PortGeometry.HitGroupTitle`, [ADR-0016](adr/0016-group-drag.md) |
| **правило действий группы** | Какие действия игра принимает от группы: один тип участников — действия этого типа, включённые **хотя бы у одного**; разные типы и все участники функциональные — **пересечение** действий, включённых **у каждого**; разные типы и хоть один не функциональный — **ничего**. «Общий предок» не ищется | `BlockPortCatalog.ComputeGroupActionIds` |

### Что значит «порт задействован»

Порт рисуется **только если к нему есть хотя бы одна связь**. Слоты раздаёт
`GridGraph.LayoutPorts()` — единственное место, где это решается, потому что слот зависит от
связей, а связями владеет граф.

Отсюда: блок с сорока действиями выглядит как блок с четырьмя, пока к нему ничего не
подключено. Каталог портов при этом полон — он отвечает «что **можно** соединить», а не «что
нарисовать».

Следствие для того, кто меняет связи: **после любого изменения связей нужен
`LayoutPorts()`**. Пропущенный вызов означает порт без полосы и линию, уходящую в пустоту.

### Что значит «удалить порт»

Удалить порт — значит снять **все его связи**: у исходящего — все уходящие линии (fan-out), у
входящего — все приходящие (fan-in). Сам порт как возможность блока остаётся в модели: набор
портов задаётся каталогом и списком действий, а не пользователем.

Связанный порт на другом конце исчезает **сам** — у него не осталось связей, и `LayoutPorts`
снял слот. Отдельного кода «удалить связанный порт» нет и быть не должно.

Удаление обязано сначала очистить ячейку тулбара источника (`ToolbarWriter.TryClear`), и только
потом убрать ребро из графа: связь — это элемент тулбара (ADR-0011), и сверка восстановит ребро
из тулбара, если элемент остался (ADR-0014).

### Уникальность

| Сторона | Правило | Почему |
|---|---|---|
| **исходящий порт** | **уникален**: принадлежит одному событию одного блока | Слить два разных события в одну точку нельзя — у линии нет источника |
| **входящий порт** | **общий**: несколько линий приходят в одну точку | «Включить» — одно действие; его могут просить разные блоки, и это нормальная схема |
| **ячейка тулбара** | **уникальна**: одна ячейка — одна связь | Две связи в одной ячейке — это одна запись в блоке, и вторая молча затёрла бы первую |

Отсюда **fan-out** (одна точка, много уходящих линий) разрешён, **fan-in** (одна точка, много
приходящих линий) разрешён, а «два события в одном исходящем порту» — нет.

Отдельно: **одинаковые связи — это не дубликаты**. Одно и то же событие на один и тот же
блок с одним и тем же действием, но на разных страницах тулбара — разные связи, и игра
исполняет их отдельно. Их число ограничено числом страниц (у таймера — десять).

Прежнее правило «вход имеет не более одного источника» **отменено** —
[ADR-0010](adr/0010-port-presentation-and-binding.md).

## 3. Связь

| Термин | Значение | В коде |
|---|---|---|
| **связь** | Направленное соединение: исходящий порт одного узла → входящий порт другого. Источник — всегда **блок**; получатель — блок или **группа** | `Vgs.Model.Edge` |
| **источник** | Узел, чей исходящий порт начинает связь. Группа источником быть не может: у неё нет тулбара, ей нечем сработать | `Edge.SourceEntityId`, `Edge.SourcePortKey` |
| **получатель** | Узел, чей входящий порт принимает связь: блок (`Edge.TargetEntityId`) или группа (`Edge.TargetGroupName`) | `Edge.TargetEntityId`, `Edge.TargetGroupName`, `Edge.TargetsGroup` |
| **линия** | То, как связь нарисована: ортогональный маршрут от точки исходящего порта к точке входящего | `Vgs.Ui.EdgeRouting` |
| **маршрут** | Последовательность горизонтальных и вертикальных отрезков линии. Всегда приходит в целевую точку **слева, двигаясь вправо**. Изгиб — на **середине** линии, а не у источника | `EdgeRouting.Build` |
| **точка ожидания** | Кружок, который едет за курсором в режиме привязки, показывая, что линия «приклеена» к мыши | `DrawPendingLine` |
| **пропорции** | Отношение высоты клиентской области к её ширине. Один X-юнит раскладки — ширина окна, один Y-юнит — высота, поэтому всё круглое проходит через поправку `AspectX`; без неё круг рисуется эллипсом | `VgsScreenDraw.ClientAspect`, `AspectX` |

Связь — это данные. Линия — это её отрисовка. Связь существует, даже если линия не
нарисована (порт не получил слот).

Связь хранит ещё и **ячейку** тулбара источника (`Edge.Cell`): именно она делает связь
работающей, потому что ячейка — это место, куда игра кладёт «получатель + действие» и
откуда потом запускает ([ADR-0011](adr/0011-toolbar-is-the-connection.md)).

**Получатель бывает двух видов, и это видно в ячейке.** Блок — элемент `BlockAction`,
группа — элемент `GroupAction` с именем группы. Одна связь на группу — это **одна** ячейка,
а не по ячейке на участника: игра сама применяет действие ко всем участникам
([ADR-0015](adr/0015-block-groups.md)). Отсюда следствие для подсчётов: fan-in группы
считается по её имени, а не по id участника, иначе группа и блок делили бы один счётчик.

Связей может быть больше, чем линий: повтор одного и того же действия на одном и том же
блоке — это отдельная связь (своя ячейка, своя страница), но **одна** линия между теми же
двумя точками. Поэтому у графа два списка: `Edges` — все связи, `Lines` — по одной на пару
портов.

## 4. Режимы указателя

Экран имеет три взаимоисключающих режима. Состояние — не набор флагов кнопок, а явные поля,
потому что режимы именно взаимоисключающие: перетаскивание, начатое во время привязки,
дралось бы с линией за указатель.

| Режим | Как включить | Что делает ЛКМ | Что делает ПКМ | Состояние |
|---|---|---|---|---|
| **обычный** | — | выбрать карточку, перетащить её; потянуть **полосу имени группы** — перетащить всю группу; «x» на полосе порта — удалить его связи | панорама | `_bindSource == null` |
| **привязка** | нажать «+» на карточке, либо «T»/«F» у блока с двумя группами | выбрать блок-получатель и открыть меню действий | **сбросить режим** | `_bindSource`, `_bindPort`, `_bindGroup` |
| **меню** | клик по получателю в режиме привязки | выбрать действие и создать связь | сбросить режим | `_menuTarget` |

Esc выходит из самого глубокого режима первым: в привязке — сбрасывает её, в обычном —
закрывает редактор.

| Термин | Значение | В коде |
|---|---|---|
| **«+»** | Круглая кнопка на карточке справа, по центру по вертикали. Диаметр — 75% высоты карточки. Нарисована инверсно: белый диск, плюс цветом фона карточки; плюс — геометрия, а не глиф шрифта. Есть только у блока, который может управлять другими и имеет **одну** группу | `PortGeometry.TryBindButton(…, PortGroup.Single, …)` |
| **«T» / «F»** | Две меньшие круглые кнопки на правой границе карточки, одна над другой, с буквой цвета фона. Заменяют «+» у блока с двумя группами: выбор группы **до** выбора получателя. Названия — «да»/«нет», а буквы — те же, что игрок видит в ванильном тулбаре | `PortGeometry.TryBindButton`, `PortGeometry.HasGroupButtons` |
| **«x» на порте** | Круглая кнопка на полосе порта, напротив точки: у исходящего слева, у входящего справа. Диаметр — 75% высоты полосы, отступ от границы — 4 пикселя; белый диск с «x» цветом фона полосы. Нажатие удаляет все связи порта. Есть только в обычном режиме | `PortGeometry.TryPortRemoveButton`, `PortGeometry.HitPortRemoveButton`, `VgsEditorScreen.RemovePortConnections` |
| **блок-источник** | Тот, от чьей кнопки начата привязка. `Node.CanDriveBlocks` — признак, что кнопка вообще есть. У группы кнопки нет никогда | `Node.CanDriveBlocks` |
| **меню действий** | Список терминальных действий получателя, из которого выбирается, что именно с ним сделают. Для группы — её собственный список, посчитанный по правилу действий группы, а не объединение списков участников | `DrawActionMenu`, `BlockPortCatalog.ComputeGroupActionIds` |
| **сообщение об отказе** | Строка в нижней панели, которая объясняет, почему связь не создалась (нет свободной ячейки, действие уже на всех страницах, блок исчез) | `VgsEditorScreen.Warn` |

## 5. Какие блоки «могут управлять другими»

Ответ даёт **интерфейс игры**, а не таблица и не флаг:

> Блок может управлять другими, если у его сущности есть компонент `IMyToolbarProvider` и его тулбар имеет тип
> `MyToolbarType.ButtonPanel` — то есть активируется собственной логикой блока.

`Vgs.Game.ToolbarProbe` читает это у живого блока; результат — `ToolbarLayout` с числом
слотов, страниц и признаком «две группы».

| Блок | Тулбар, который он запускает сам | Может управлять |
|---|---|---|
| Таймер | да, `ButtonPanel` | да |
| Сенсор | да, `ButtonPanel`, две группы | да |
| Event controller | да, `ButtonPanel`, две группы | да |
| Кокпит | да — тулбар «при блокировке цели»; его же панели `Ship` и `BuildCockpit` — панели игрока | да, но не через панели игрока |
| Панель кнопок | да, `ButtonPanel` | да |
| Батарея, реактор, конвейер, броня | нет тулбара | **нет** |

Два ответа, которые кажутся верными и неверны:

- **флаг `ShowInToolbarConfig`** — говорит, что блок можно **приводить в действие**, то есть
  описывает противоположное отношение (блок как получатель);
- **«у блока есть события в игре»** — недостаточно: батарея умеет сообщать C#-коду о смене
  заряда, но своего тулбара у неё нет, и связь положить некуда.

Блок, которого нет в курируемой таблице имён событий, но у которого есть тулбар, **является
источником**: он получает общее событие `Triggered`. Интерфейс важнее таблицы.

## 6. Сущности экрана и камеры

| Термин | Значение | В коде |
|---|---|---|
| **камера** | Точка поля, показанная в левом верхнем углу холста | `_camera` |
| **зум** | Масштаб поля. Меняется колесом вокруг курсора | `_zoom` |
| **панорама** | Сдвиг камеры. ПКМ или СКМ | `_panning` |
| **холст** | Область между шапкой и нижней панелью, где рисуется поле | `GetCanvasRect` |
| **hit-test** | Проверка, что находится под указателем. Для карточек и портов живёт рядом с геометрией, чтобы нарисованное и кликабельное совпадали | `PortGeometry.HitNode` |
| **отсечение** | Пропуск того, что не видно: карточек — по экрану, линий — по пределу `MaxRenderedEdges`, прямоугольников — пересечением с холстом | `DrawNodes`, `VgsScreenDraw.RectClipped` |

## 7. Слои кода

Слова, которые нельзя путать: это не стилистика, а правило зависимостей
([ADR-0003](adr/0003-layering.md)).

| Слой | Что внутри | Чего не содержит |
|---|---|---|
| `Vgs.Core` | Логирование, константы, строки, фасад сессии | игровой логики |
| `Vgs.Model` | `Node`, `NodeKind`, `GroupMemberActions`, `Port`, `Edge`, `GridGraph`, `BlockPortCatalog`, `NodeStateFormat` | **ни одной ссылки на игру** |
| `Vgs.Game` | `GridGraphBuilder`, `VgsTerminalControls`, `ToolbarProbe`, `ToolbarWriter`, `NodeStateStore` | отрисовки |
| `Vgs.Ui` | `VgsEditorScreen`, `VgsScreenDraw`, `PortGeometry`, `EdgeRouting` | чтения живых блоков при рисовании |

`Vgs.Model` — единственный слой, который можно проверить, не запуская игру. Поэтому правила
графа (нет петли, нет дубликата, нет связи на несуществующий порт, удаление узла удаляет его
связи, порт рисуется только при наличии связи, группа живёт при видимом участнике, правило
действий группы) живут в `GridGraph` и `BlockPortCatalog`, а не в UI.

## 8. Чего в словаре нет

- **«Терминал»** — это панель игры, а не наш экран. Наш экран — **редактор**.
- **«Виджет»**, **«контрол»** — в разрешённом API их нет: всё нарисовано вручную. Поэтому
  «кнопка» здесь всегда означает прямоугольник с hit-test, а не элемент GUI игры.
- **«Событие»** в смысле C# (`event`) и **событие** в смысле порта — разные вещи. Второе
  пишется «исходящий порт» или «событие блока».
