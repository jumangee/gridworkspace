# Ревизия организации кода VGS

Дата: 2026-11-23. Автор: независимый агент-ревизор (роль «сторонний агент»).

Цель — оценить **структуру** кода (классы, дублирование, единая ответственность, качество
абстракций), а не его соответствие принятым ADR и не корректность поведения. Выводы
оцениваются по существу, «не взирая на то, что уже закреплено в решении и ADR», кроме
объективных фактов (границы API, ограничения C# 7.3 / .NET 4.x, запреты вайтлиста).

---

## 1. Вердикт (коротко)

Код **не является «лапшой»** в целом: слои `Vgs.Core` / `Vgs.Model` / `Vgs.Game` / `Vgs.Ui`
выделены чисто, правило зависимостей соблюдено, каждая граница с игрой обёрнута в
`try/catch`, дисциплина «без аллокаций в кадровых путях» выдержана. Это редкий по качеству
мод-код.

Подозрение на «лапшу» подтверждается **ровно в одном месте** — классе
[`Ui/VgsEditorScreen.cs`](../../src/VGS.Mod/Data/Scripts/VGS/Ui/VgsEditorScreen.cs)
(~4900 строк, ~80 полей, ~110 методов), который один несёт шесть разных ответственностей.
Внутри он аккуратно разбит на секции и обильно задокументирован, поэтому это «бог-класс», а
не спутанная логика, — но масштаб уже сейчас мешает развитию.

Главный риск для планов — не столько сам бог-класс, сколько **два отсутствующих абстрактных
понятия**: «состояние блока» (повреждение/заполненность/заряд) и «специфика категории
блока». Оба плана (живая схема, больше частных правил отображения) упираются в них, а
сейчас их нет вовсе.

## 2. Метод и рамки

Просмотрены все `.cs` в `src/VGS.Mod` (слои `Vgs.Core`/`Vgs.Model`/`Vgs.Game`/`Vgs.Ui`)
и ключевая документация (`03-architecture.md`, `06-terminology.md`, `ROADMAP.md`, `adr/`).
`tests/OfflineChecks.cs` (утверждения офлайн-шлюза) не перечитывался: ревизия — про структуру
продакшен-кода, а не про тесты.

**Не проверялось** (по правилам роли — агенты не запускают игру):

- поведение в игре, производительность в реальной сессии, мультиплеер;
- корректность вызовов API против сборок игры (это зона `verify-compile` /
  `check-whitelist`, они здесь не прогонялись);
- соответствие кода ADR (намеренно выведено за рамки — задача про структуру).

## 3. Что хорошо — и трогать это не нужно

Эти решения по структуре не требуют изменения, и в roadmap они не попадают:

- **Слои и направление зависимостей** (`Model` без ссылок на игру, `Game` — единственный
  читатель мира, `Ui` не читает мир при рисовании). Разделение последовательное.
- **`Vgs.Model`** — чистые данные с инвариантами в `GridGraph`; офлайн-проверяемость
  выдержана. `ToolbarPlanner`/`CellContents`/`NodeStateFormat`/`GridViewFormat`/
  `BlockSearch`/`TextEditor` — образцовые маленькие типы «одна причина измениться».
- **`Vgs.Game`** — по типу на границу (`ToolbarProbe`, `ToolbarWriter`, `NodeStateStore`,
  `GridViewStore`, `TerminalJump`, `EventControllerProbe`, `EventControllerKeeper`), каждый
  документирует свой контракт и сам гасит исключения.
- **`VgsScreenDraw`** — единственная точка вызова API отрисовки, изолирует
  `MyScreenSpace*`, координатные пространства и текстуры. Смена способа отрисовки меняет
  один файл.
- **`EdgeRouting`** — чистая геометрия маршрута, изолирована и офлайн-проверяема. План
  «кривые линии» ложится сюда без перестройки (см. §5.3).

## 4. Находки, ранжированные от самых важных к менее важным

Приоритеты `P0`–`P5`. `P0` — самое важное (блокирует планы), `P5` — гигиена, которую можно
не делать вовсе.

### P0 — В модели нет понятия «состояние блока», и refresh не разделяет структуру и состояние

**Где.** [`Model/Node.cs`](../../src/VGS.Mod/Data/Scripts/VGS/Model/Node.cs) не имеет ни
одного поля состояния (нет повреждения, заполненности, заряда).
[`Game/GridGraphBuilder.cs`](../../src/VGS.Mod/Data/Scripts/VGS/Game/GridGraphBuilder.cs)
делает в `Refresh` полный проход: блоки → группы → сверка тулбаров → `LayoutPorts`
(строки 87–166). Обновление идёт раз в `RefreshIntervalFrames = 90` кадров
(`VgsEditorScreen.cs:334`).

**Почему это блокирует планы 1 и 2.** «Схема станет живой, обновление ~2 раза/сек» требует
дешёвого пути «обновить только состояние видимых узлов». Сейчас такого пути нет: единственный
`Refresh` перечитывает структуру, группы и тулбары целиком. Два раза в секунду гонять его на
большом корабле дорого, а болтать состояние на него нельзя — `Refresh` пересоздаёт `Port`
при смене списка действий и чреват миганием раскладки.

**Что требуется (этап 4, работа 1).**

1. Ввести снимок состояния (`BlockState`/`NodeState`) на `Node` (или параллельной таблицей
   `Dictionary<long, BlockState>`): минимум «повреждение», дальше — расширяемое поле под
   частные показатели категорий.
2. Разделить чтение на два прохода: **структурный** (как сейчас, по таймеру — что
   добавилось/исчезло/изменилось в тулбарах) и **состояния** (2 Гц, только видимые узлы,
   без перестройки портов/групп/тулбаров).
3. Зафиксировать, что `Vgs.Ui` читает состояние из снимка, а не из мира (правило ADR-0003
   распространяется на новый вид данных).

### P1 — Специфика категорий блоков размазана ad-hoc флагами и подстрочным матчингом

**Где.** Специфика event controller живёт в **шести+ местах**: `Node.IsEventController`,
`Node.StatusText`, `Node.Watched`, `Node.WatchEventId`, `Node.HasStatusLine`
([`Node.cs:591–643`](../../src/VGS.Mod/Data/Scripts/VGS/Model/Node.cs)),
`GridGraph.TryAddWatch/RemoveWatch/SyncWatched/…`, `GridGraphBuilder.RefreshControllerState`,
`EventControllerProbe`, `EventControllerKeeper`, `NodeStateStore` (список в хранилище),
`PortGeometry` (жёлтые полосы). Категория блока определяется
[`BlockPortCatalog.ResolveFamily`](../../src/VGS.Mod/Data/Scripts/VGS/Model/BlockPortCatalog.cs:75)
— цепочка из ~30 `Contains(subtype)` + курируемая таблица `FamilyEvents`.

**Почему это блокирует план 2.** «Заряд батареи, заполненность контейнера, … специфичных
правил отображения будет сильно больше» при текущем устройстве означает: ещё по 3–5 полей на
общий `Node` на каждую категорию и ещё по классу-пробику на категорию. `ResolveFamily` на
подстроках не масштабируется (уже сейчас `airvent` vs `oxygen`, `cargocontainer` vs
`cargosmall` — ручные оговорки).

**Что требуется (этап 4, работа 2).**

1. Общее свойство (повреждение) вынести в `P0`-состояние; частные свойства категорий — в
   отдельный описатель категории/трейта, а не флагами на `Node`.
2. Заменить `ResolveFamily` на явный описатель «категория → события + какие состояния
   читать + как отображать», с деградацией к generic-поведению (как сейчас `Triggered`).
3. Перенести event controller на ту же механику как первый (и самый крупный) потребитель:
   его нынешние 5 полей `Node` — готовый кейс для проверки, что новая абстракция решает
   «общее отдельно, частное отдельно».

### P2 — `VgsEditorScreen` — бог-класс, который дальше будет только расти

**Где.** [`Ui/VgsEditorScreen.cs`](../../src/VGS.Mod/Data/Scripts/VGS/Ui/VgsEditorScreen.cs)
(~4900 строк). Один класс несёт:

| Ответственность | Примерные методы |
|---|---|
| жизненный цикл экрана | `OnOpened/OnUpdate/OnDraw/OnHandleInput/OnClosed/OnCancelling` |
| состояние вида (камера/зум/режим) | `RememberSavedView`, `SaveViewIfChanged`, `ToggleShowHidden` |
| текстовое поле поиска | `HandleSearchKeyboard`, `PlaceCaretAtPointer`, `EnsureFieldLayout`, `CopySearchText`, `PasteSearchText`, `DrawSearchField`, `PrefixWidth`, `CaretVisible` |
| 4 режима указателя | `HandleCanvasInput`, `HandleBindInput`, `HandleWatchInput`, `HandleMenuInput`, `BeginBind/CancelBind`, `BeginWatch/CancelWatch` |
| hit-testing | `HitTest`, `HitTestCardButton`, `HitTestRemoveButton`, `HitTestWatchRemoveButton`, `UpdateHover` |
| геометрия окна | `GetCanvasRect`, `GetBottomBarRect`, `GetCloseButtonRect`, `GetModesButtonRect`, `GetSearchFieldRect`, `GetMenuRect`, … |
| отрисовка всего | `DrawGrid`, `DrawNodes`, `DrawNode`, `DrawPortBar(s)`, `DrawWatchBars`, `DrawEdges`, `DrawWatchLines`, `DrawGroupFrames`, `DrawActionMenu`, `DrawModesMenu`, `DrawSearchField`, `DrawHeader`, `DrawBottomBar`, … |

**Почему это риск.** Каждый из пяти планов добавляет сюда работу: живое состояние — новые
ветки в `DrawNode`/`Update`; кривые — правка `DrawRoute`/`DrawDashedRoute`; выпадающее меню
узла — **ещё один режим указателя** (`HandleNodeMenuInput` + `DrawNodeMenu` + hit-test);
субгриды — новые рамки/видимость в `DrawNodes`/`DrawGroupFrames`. Класс, который уже ~4900
строк, станет ~7000+ и окончательно перестанет быть читаемым.

**Что требуется (этап 4, работа 3).** Разбить, не меняя поведения и сохраняя инварианты
(«UI не читает мир при рисовании», «нет аллокаций в кадровых путях», каждый вход из игры в
`try/catch`). Предлагаемое направление:

1. **Экран-оболочка** (`VgsEditorScreen`) оставляет жизненный цикл, маршрутизацию режимов
   и композицию отрисовки. Состояние вида выносится в отдельный `ViewState`.
2. **`SearchField`** (текст + каретка + выделение + буфер + отрисовка + hit-test) — целиком
   в отдельный тип; `TextEditor`/`TextClipboard`/`BlockSearch` уже вынесены и под него
   ложатся.
3. **Обработчики режимов** — по типу на режим (idle/bind/watch/menu), либо частичные классы.
4. **Рендер** — рисование карточки/портов/линий/групп в отдельный тип (или `partial`), чтобы
   каждая новая визуальная фича (живые индикаторы, кривые, меню узла) попадала в свой файл.

Это самый трудоёмкий пункт, и его можно делать параллельно с `P0`/`P1` (разные слои), но
**до** того, как в UI начнут добавляться живые индикаторы и меню узла.

### P3 — Точечные дублирования и общий хелпер разрешения сущности

Низкий риск, быстрые правки, но именно такие места размножаются с каждым новым режимом.

1. **Средний клик — панорама продублирована** дословно в
   [`HandleBindInput`](../../src/VGS.Mod/Data/Scripts/VGS/Ui/VgsEditorScreen.cs:2104)
   и [`HandleWatchInput`](../../src/VGS.Mod/Data/Scripts/VGS/Ui/VgsEditorScreen.cs:2181)
   (~16 одинаковых строк). Вынести в один `PanWithMiddleButton(mouse, canvasTopLeft, canvasSize)`.
2. **Сброс состояния взаимодействия продублирован** между `CancelBind` (:2581),
   `CancelWatch` (:2248), `ClearHoverHighlights` (:1086), `BeginWatch`/`BeginBind`
   (одни и те же поля гасятся в нескольких местах). Собрать в один метод сброса.
3. **Разрешение `entityId → IMyTerminalBlock` продублировано** минимум в пяти местах:
   `VgsEditorScreen.ResolveBlock` (:2996), `EventControllerProbe.Resolve` (:601),
   `GridGraphBuilder.SafeNameOf` (:314, инлайн `GetEntityById`), `NodeStateStore.SavePosition`
   (:121, инлайн), `EventControllerKeeper.TryApply` (:217, инлайн). Один
   `Vgs.Game`-хелпер `TryResolveTerminalBlock(long, out IMyTerminalBlock)` с тем же
   троттлингом уберёт пять копий и единый тег лога.

### P4 — Граф завязан на один грид

**Где.** [`Model/GridGraph.cs`](../../src/VGS.Mod/Data/Scripts/VGS/Model/GridGraph.cs) хранит
единственный `GridEntityId` (строка 78) и строится из одного `IMyCubeGrid`
(`GridGraphBuilder.Build/Refresh`). Субгриды сейчас входят только как **участники групп**
через терминальную систему логической группы (`GridGraphBuilder.ReadGroups`).

**Почему это блокирует план 5.** «На схеме можно смотреть не только текущий грид, но и
субгриды; каждый грид показан почти как группа, можно скрыть/показать целый грид» требует:
признак грида у узла, агрегированную видимость по гриду и рамку-группу по гриду. Сейчас узла
субгрида в графе нет вовсе (только в `Node.Members` группы как `long`).

**Что требуется (этап 4, работа 4).** Ввести идентичность грида на узле и много-гридовое
представление графа (или список графов с общим холстом), переиспользовав механику
рамок-групп для «рамки грида». Делать после `P0` (живое состояние тоже захочет знать грид)
и до плана 5.

### P5 — Гигиена (необязательно)

- [`GridGraphBuilder.SyncGroups`](../../src/VGS.Mod/Data/Scripts/VGS/Game/GridGraphBuilder.cs:374)
  несёт **два подряд `<summary>`** (строки 374–391 и 392–413) — задвоенный XML-комментарий,
  который разъезжается с текстом; слить в один.
- Палитра `Col*` (~25 констант цвета) лежит в `VgsEditorScreen.cs:69–130`, тогда как числа
  и id по правилу живут в `VgsConstants`. Вынести в `VgsConstants` (или отдельный
  `VgsPalette`), когда класс будет делиться — сейчас трогать не обязательно.
- `VgsConstants.cs` содержит два публичных типа (`VgsConstants` и `VgsText`) в одном файле —
  разнести по файлам.
- [`Model/Node.cs`](../../src/VGS.Mod/Data/Scripts/VGS/Model/Node.cs) содержит 11 типов в
  одном файле. Это задокументированное решение (ADR-0007, изменяемые DTO), менять не нужно;
  но при введении состояния (`P0`) файл стоит разделить на `Node`, `Port`/`PortGroup`,
  `Edge`, `WatchTarget`/`GroupMemberActions`, `ToolbarLayout`/`ToolbarCell`.

## 5. Соответствие пяти планируемым направлениям

| # | Планируемое направление | Что уже готово | Что потребует правок |
|---|---|---|---|
| 1 | Живая схема (повреждение/заполненность/заряд, ~2 Гц, видимые узлы) | Снимок `GridGraph` + троттлинг refresh | **`P0`** (состояние + раздельный refresh), `P2` (индикаторы в рендере), `P3` |
| 2 | Больше специфики узлов; общее (повреждение) vs частное (заряд, заполненность) | `BlockPortCatalog`, `Node.StatusText` как прецедент | **`P0` + `P1`** (трейты категорий вместо флагов), `P2` |
| 3 | Кривые линии; динамический цвет/прозрачность от условий | `EdgeRouting` изолирован и офлайн-проверяем; `VgsScreenDraw.Segment` | Замена `EdgeRouting.Build` на кривые + функция стиля ребра (цвет/альфа от состояния концов) — **локально**, слой не менять; `P0` даст источник условий |
| 4 | Выпадающее меню на узле для управления блоком | `ActionMenu` как прецедент меню + hit-test | **`P2`** (новый режим указателя + отрисовка + геометрия), `Vgs.Game`-обработчик действия |
| 5 | Субгриды; грид как рамка-группа; скрыть/показать грид | Рамки групп (`PortGeometry.TryGroupFrame`), агрегированная видимость | **`P4`** (много-гридовой граф), `P2` |

## 6. Резюме для roadmap

Пошаговый план **как** устранять находки (с порядком выполнения, действиями по файлам и
критериями готовности каждого шага) — [`code-organization-plan.md`](code-organization-plan.md).

Изменения **требуются**. Порядок (см. `ROADMAP.md`, «Этап 4»):

1. **P0** — состояние блока + раздельный refresh структуры/состояния (фундамент планов 1–2).
2. **P1** — трейты категорий вместо ad-hoc флагов и подстрочного матчинга (фундамент плана 2).
3. **P2** — разбить `VgsEditorScreen` (фундамент планов 1, 2, 4, 5).
4. **P4** — много-гридовой граф (фундамент плана 5).
5. **P3** — точечная дедупликация (можно параллельно с любым из вышестоящих).
6. **P5** — гигиена (опционально).

`P0`/`P1`/`P4` — слой модели и Game; `P2`/`P3` — слой Ui. Их можно вести двумя параллельными
линиями, но внутри каждой линии порядок важен.
