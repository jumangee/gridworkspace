# План работ по устранению замечаний ревизии организации кода

Дата: 2026-11-23. Основание: [`code-organization-review.md`](code-organization-review.md)
(находки P0–P5). Этот документ — пошаговый план **как** устранять находки, в порядке
выполнения (не путать с порядком важности из ревизии: порядок важности отвечает «что
важнее», порядок здесь — «в какой последовательности безопаснее делать»).

Правила, общие для всех шагов (из [`AGENTS.md`](../../AGENTS.md) и ADR):

- стек — только C# 7.3 / .NET Framework 4.x (без `string?`, без `async/await`, без
  транспилеров и NuGet);
- реорганизация **не меняет поведение**: каждый шаг заканчивается зелёными шлюзами и, для
  шагов, видимых игроку, — регрессионным списком [`review/regressions.md`](regressions.md);
- изменение модели графа или ответственности типа правит [`03-architecture.md`](../03-architecture.md)
  и, при новом понятии, [`06-terminology.md`](../06-terminology.md) **в том же изменении**;
- если шаг противоречит принятому ADR — сначала [`joint-review.md`](joint-review.md), вердикт
  как ADR, и только потом код. Молчаливая правка в любую сторону запрещена;
- каждый вход из игры (`Update`, `Draw`, `HandleInput`, колбэки) остаётся в `try/catch` с
  `VgsLog`; никаких аллокаций в кадровых путях (`OnDraw`, `OnHandleInput`, `OnUpdate`).

Где шаг меняет модель (`Vgs.Model`), он **обязан** добавлять/править утверждения в
[`tests/OfflineChecks.cs`](../../tests/OfflineChecks.cs) — это единственный шлюз, проверяющий
логику без игры.

### 1.1. Один хелпер разрешения сущности

Вынести общий `Vgs.Game`-хелпер (новый файл `Game/EntityResolver.cs`) и заменить пять копий:

| Где сейчас | Строка (на дату ревизии) |
|---|---|
| `VgsEditorScreen.ResolveBlock` | `VgsEditorScreen.cs:2996` |
| `EventControllerProbe.Resolve` | `EventControllerProbe.cs:601` |
| `GridGraphBuilder.SafeNameOf` (инлайн `GetEntityById`) | `GridGraphBuilder.cs:314` |
| `NodeStateStore.SavePosition` (инлайн) | `NodeStateStore.cs:121` |
| `EventControllerKeeper.TryApply` (инлайн) | `EventControllerKeeper.cs:217` |

Контракт: `public static bool TryResolveTerminalBlock(long entityId, out IMyTerminalBlock block)`,
внутри `try/catch` + `VgsLog.Throttled` с единым тегом (сейчас теги `resolve-block`,
`ec-resolve`, `watch-name`, `nodestate.gone`, `ec-keeper-apply` разъезжаются). Логирование
вызова из `Vgs.Ui` разрешено (Ui → Game из ввода, не из отрисовки).

Сделано: `Game/EntityResolver.cs`, контракт ровно такой. Одно уточнение к контракту — **что
осталось у вызывающих**. Единый тег получила только *неудача разрешения* (бросок исключения),
потому что это одна и та же неисправность: раньше её писали пять тегов, и в логе она выглядела
как пять разных проблем. Прочие теги остались там, где они описывают другое событие:
`nodestate.gone` («блок исчез, позиция не сохранена» — штатный исход, а не ошибка),
`watch-name` и `toolbar-resolve` (блок нашёлся, но чтение из него не удалось). Свести их в
`resolve-block` значило бы соврать в логе и — по правилу из `VgsLog` — дать одному частому
событию заглушить редкое. Отсутствие блока вообще не логируется: это норма, и вызывающий сам
говорит о ней словами игрока.

Заменены все пять копий и, дополнительно, шестая — `GridGraphBuilder.ResolveToolbar`, которую
ревизия не перечислила, но которая повторяла те же две строки.

### 1.2. Панорама средним кликом — в один метод

Дубликат в `HandleBindInput` (`VgsEditorScreen.cs:2104`) и `HandleWatchInput` (:2181).
Вынести `PanWithMiddleButton(mouse, canvasTopLeft, canvasSize)` и вызвать из обоих.

Сделано: `PanWithMiddleButton` — тонкая обёртка над `PanWhileHeld(buttonDown, …)`, которая
принимает состояние кнопки параметром. Через неё же панорамирует и холст в обычном режиме
(ПКМ или СКМ): это третья копия тех же строк, и её тоже убрали. Порядок проверок и правило
«якорь переживает уход указателя за холст» сохранены дословно — поведение не изменилось.

### 1.3. Сброс состояния взаимодействия — в один метод

Одни и те же поля гасятся в `CancelBind` (:2581), `CancelWatch` (:2248),
`ClearHoverHighlights` (:1086), `BeginWatch`/`BeginBind`. Собрать общий
`ResetPointerOverlay()` (сброс `_hoverNode/_hoverButton/_hoverRemoveNode/_hoverRemovePort/
_hoverWatchRemoveNode/_hoverWatchRemoveTarget/_panning`), оставив в `CancelBind`/`CancelWatch`
только их собственные поля (`_bindSource`/`_bindPort`/`_bindGroup`, `_watchSource`).

Сделано тремя методами вместо одного, по одной причине: у трёх мест разный набор полей, и
общий метод заставил бы кого-то гасить лишнее.

| Метод | Гасит | Кто зовёт |
|---|---|---|
| `ClearHoverTargets()` | шесть полей наведения | `UpdateHover`, оба жеста ввода, `OpenActionMenu` |
| `ClearHoverHighlights()` | то же + две подсветки поля поиска | `DropNodeReferences`, открытие меню режимов |
| `ResetPointerOverlay()` | то же + `_panning` | `CancelBind`, `CancelWatch` |

`ClearHoverHighlights` намеренно **не** трогает `_panning`: до правки он его не трогал, а
менять это в шаге, который не меняет поведение, нельзя. `BeginWatch` больше не гасит
`_panning` сам — за ним стоит `CancelBind()`, который это делает; `BeginBind` оставил
`_panning = false` при себе, потому что гасить наведение в начале привязки значило бы снять
подсветку карточки, на которую игрок только что нажал.

## Шаг 2 — Снимок состояния блока и раздельный refresh (P0)

**Статус:** выполнен 2026-11-23. Четыре шлюза зелёные: `COMPILE OK — 32 file(s)`,
`WHITELIST OK — 158 refs` (+`IMySlimBlock`, `BlockState`), `REVIEW OK`, `OFFLINE OK — 1266
checks` (+31 утверждение в новом разделе «block state snapshot»). Визуально ничего не
изменилось: индикатор повреждения — это Этап 5.1, сюда не входит.

**Цель:** ввести понятие «состояние блока» как отдельный снимок в модели и разделить чтение
мира на структурный проход (редкий) и проход состояния (частый, дёшево). Это фундамент
Этапов 5.1 и 5.2. Пока что состояние — только «повреждение» (`Integrity`); заряд/заполненность
придут в Этапе 5.2 через механику Шага 3.

### 2.1. Тип состояния в модели

Новый тип `Model/BlockState.cs` (изменяемый DTO, ADR-0007), **без** ссылок на игру:

- `float Integrity` — целостность 0..1 (общее для всех блоков);
- `float[] Metrics` или `Dictionary<string, float>` — зарезервированная расширяемая часть под
  частные показатели категорий (заряд, заполненность). Решение «массив с ключом-индексом из
  описателя категории» против «словарь» принять в Шаге 3 — здесь достаточно заложить поле и
  договориться, что в кадровом пути по нему не аллоцируют (заполняется на 2 Гц, читается
  из отрисовки только по индексу/чтением).

Добавить поле на `Node` (`Model/Node.cs`): `public readonly BlockState State` (всегда создано,
чтобы отрисовка не проверяла `null` каждый кадр). Состояние — **память, не сохраняемая
сущность**: в `NodeStateStore`/`MyModStorageComponent` не идёт.

Сделано: `Model/BlockState.cs` — `Integrity` (0..1, с допуском `IntegrityTolerance` и зажимом
в `SetIntegrity`) плюс **массив** `Metrics` под частные показатели, а не словарь: решение
«массив с индексом из описателя» принято здесь, потому что словарь в кадровом пути означал бы
хэш строки и аллокацию энумератора шестьдесят раз в секунду. Пока ни одна категория метрик не
публикует, все состояния делят один пустой массив `NoMetrics`, так что кадровый путь ничего
не находит и ничего не аллоцирует. `Node.State` создаётся в обоих конструкторах — у группы
тоже, чтобы отрисовка не спрашивала, какой это узел.

### 2.2. Два прохода в `GridGraphBuilder`

Сейчас `Refresh` (`GridGraphBuilder.cs:87-166`) делает всё: блоки → группы → сверка тулбаров →
`LayoutPorts`. Разделить:

- **`Refresh`** оставить структурным (переименовать при необходимости в
  `RefreshStructure`, сохранив публичную точку вызова) — без изменений логики;
- **новый `RefreshState(GridGraph graph, IReadOnlyCollection<long> visibleEntityIds)`** —
  только читает `Integrity` (и, позже, метрики) для переданных id и пишет их в
  `node.State`, **не** трогая порты/группы/тулбары и **не** вызывая `LayoutPorts`.

Совместное правило (важно): состояние — это **снимок**, читается из мира только в `Vgs.Game`,
отрисовка берёт `node.State`. Правило ADR-0003 «Ui не читает мир при рисовании»
распространяется на состояние.

Сделано: `Refresh` не переименован — он и так читается как «структурный проход», а
переименование тронуло бы семь вызовов ради слова; роль зафиксирована в его `<summary>`.
`RefreshState(GridGraph, IList<long>)`: `IList` вместо `IReadOnlyCollection`, потому что
проход индексирует набор, а `IReadOnlyCollection` индексатора не имеет и заставил бы либо
копировать, либо ходить через `foreach` с аллокацией энумератора на каждом тике.

Запись идёт через `GridGraph.ApplyIntegrity(long, float)` — единственную запись состояния в
модели: она трогает `Node.State` и ничего больше. Это и есть проверяемый инвариант шага.

### 2.3. Видимые узлы

Набор «видимых сейчас» уже умеет считать отрисовка (`DrawNodes` culling,
`VgsEditorScreen.cs:3496-3508`). Вынести эту арифметику (прямоугольник холста + границы
карточки) в один метод, который можно вызвать и из прохода обновления, чтобы на 2 Гц
опрашивать только узлы в кадре. Если «видимые» окажется дорого/неустойчиво вычислять —
первая итерация допустима с опросом **всех** узлов графа (ограничено
`VgsConstants.MaxRenderedBlocks`), а сужение до видимых — отдельной доработкой; решение
зафиксировать комментарием/ADR-заметкой, не городить преждевременно.

Сделано сразу с сужением, отступление не понадобилось: арифметика оказалась дешёвой и уже
существовала. `IsCardOnCanvas(node, topLeft, size)` — тот же предикат, что был внутри цикла
`DrawNodes`, теперь вызванный из обоих мест; `CollectVisibleNodeIds(List<long>)` заполняет
переиспользуемый список теми же карточками в том же порядке и под тем же потолком
`MaxRenderedBlocks`. Одно определение «видимого» на оба прохода — иначе проход состояния
опрашивал бы карточки, которых не видно, и пропускал бы те, что видно.

### 2.4. Таймер 2 Гц в экране

В `VgsEditorScreen` уже есть собственный счётчик кадров `_screenFrame` (`OnUpdate`,
`VgsEditorScreen.cs:964`, ADR-0026 — счётчик экрана, а не `VgsSession.Frame`). Добавить
константу `StatePollIntervalFrames` (~30 кадров) в `VgsConstants` и в `OnUpdate`, не чаще
интервала, вызывать `RefreshState` вместо полного `Refresh` (полный `Refresh` остаётся на
своём `RefreshIntervalFrames = 90`).

Сделано: `VgsConstants.StatePollIntervalFrames = 30`, свой счётчик `_lastStatePollFrame`
(общий с `_lastRefreshFrame` связал бы проходы и опустил бы частый до частоты редкого),
`RefreshNodeState()` в `OnUpdate` под `try/catch`. Дополнительно проход вызывается **в конце
`RefreshFromGrid`**: структурный проход мог только что создать узлы, и без этого их состояние
оставалось бы дефолтным ещё полсекунды — ровно у тех блоков, которые игрок только что
поставил.

### 2.5. Отрисовка (заглушка-проверка механики)
Пока без визуальных изменений: убедиться, что `State` заполняется и доступен в `DrawNode`.
Реальное отображение повреждения — Это ЭТАП 5.1, не сюда. В `OfflineChecks` добавить
утверждение на любое чистое правило, введённое в 2.2/2.3 (например, «`RefreshState` не
пересоздаёт порты» — проверяется через инвариант, что после прохода состояния списки
`Port` те же по ссылкам).

Сделано: раздел «block state snapshot» в `tests/OfflineChecks.cs` (31 утверждение). Проверяет
ровно то, что нельзя увидеть глазами до Этапа 5.1: у узла и у группы всегда есть состояние;
дефолт — «не известно, что повреждён»; зажим 0..1 и допуск; чтение/запись метрики по индексу
не бросает на индексе, которого у категории нет; и главное — **после записи состояния
объекты `Port` те же по ссылке, их слоты и число узлов/рёбер/групп не изменились**, а запись
для исчезнувшего узла возвращает `false` и не создаёт узел. Это и есть инвариант
«проход состояния ничего не перестраивает».

### 2.6. Индикатор повреждения (сделано по запросу владельца продукта, сверх плана)

План оставлял визуализацию Этапу 5.1. Владелец продукта попросил показать повреждение
сразу, поэтому индикатор вошёл в этот шаг — но отдельным решением, а не «заодно»:
[ADR-0028](../adr/0028-block-damage-band.md).

Правило: **ширина красной полосы справа на карточке равна повреждению** (1 − целостность),
70% целостности → 30% карточки, 50% → половина, 100% → полосы нет. Прозрачность 50%, во всю
высоту карточки, под рамкой, подписями, полосами портов и кнопками. Геометрия —
`PortGeometry.TryDamageRect`, значение — `Node.State` (не из мира), порог — `BlockState.IsDamaged`.

Офлайн-раздел «damage band on the card» — 30 утверждений. Шлюз проверен подстановкой трёх
дефектов: инверсия дроби (`Integrity` вместо `1 − Integrity`) роняет 4 утверждения, снятая
проверка `IsGroup` — одно, снятый зажим по карточке в `FitDamageBand` — два. Превью для сверки
глазами — [`damage-band-preview.png`](../01-research/images/damage-band-preview.png), сборка
`python tools/icon-atlas/damage_band_preview.py`.

**Исправлено по результату первого показа в игре (2026-11-24).** Два дефекта, оба записаны в
[`regressions.md`](regressions.md) как R-011 и R-012:

1. **Полоса рисовалась на всю ширину экрана.** Защита от субпиксельной ширины сравнивала
   нормализованную величину с `1f` — с целым экраном, а не с пикселем, — поэтому условие было
   истинно всегда. Правило перенесено в `PortGeometry.FitDamageBand` (графовые единицы, зажим
   по карточке) и покрыто офлайн-утверждениями: в слое отрисовки его нельзя было проверить, а
   значит и поймать до игры. Урок общий: **правило, которое решает картинку, должно жить там,
   где его можно проверить без игры.**
2. **Игра стояла на паузе, пока открыт редактор.** Пауза останавливает симуляцию, поэтому урон
   было негде получить, а индикатору — нечего показать. Снята
   ([ADR-0029](../adr/0029-editor-does-not-pause.md)), `UpdateOnPause` по-прежнему не
   включается, часы экрана — свои кадры.

Дополнительно: в лог добавлена одна строка за сессию —
`state pass: N of M visible card(s) read, K damaged`. Она разделяет три причины, которые на
экране выглядят одинаково: проход не доходит, карточек нет, значения целые. Именно эта строка
подтвердила, что чтение состояния работает (`9 of 9 read, 1 damaged`), и сузила поиск до
отрисовки.

## Шаг 3 — Описатель категорий блоков и миграция event controller (P1)

**Цель:** заменить подстрочный матчинг `ResolveFamily` (~30 `Contains`) и ad-hoc поля event
controller на общем `Node` на **описатель категории**: общее (повреждение) отдельно, частное
(заряд/заполненность/событие контроллера) — по категории. Фундамент Этапа 5.2.

Это самый проектный шаг — **сначала ADR**, потом код.

### 3.1. ADR: категория блока как описатель

Написать ADR (следующий номер, например `0028`) с: контекстом (5 полей event controller на
`Node`, `ResolveFamily` на подстроках, план «специфики будет сильно больше»), альтернативами
(словарь семейств как сейчас; enum + описатель; трейт-интерфейсы; перенос всей специфики в
Game) и последствиями. Зафиксировать как минимум:

- `ResolveCategory(subtypeId) -> BlockCategory` (enum), порядок проверок от специфичного к
  общему (как сейчас `eventcontroller` раньше `cockpit`);
- описатель категории отвечает: **какие события** (курируемая таблица, деградация к
  `Triggered`) и **какие метрики состояния читать** (ключи для `BlockState.Metrics`);
- где живёт специфика event controller (рекомендация ниже, 3.3);
- что «может управлять» (`CanDriveBlocks`) и «event controller» (`IMyEventControllerBlock`)
  остаются фактами, читаемыми из игры в `Vgs.Game`, — описатель модели их **не** выводит из
  имени подтипа (иначе сломается поддержка блоков других модов, ADR-0011/0017).

### 3.2. `BlockCategory` + описатель в модели

В `Model` ввести `BlockCategory` (enum) и описатель (таблица «категория → события + ключи
метрик»), переписав `BlockPortCatalog.ResolveFamily`/`FamilyEvents` на него. Поведение
`FillEvents`/`FillActions` не меняется — это перенос таблицы, не её логика.

### 3.3. Вынести специфику event controller с общего `Node`

Наименее рискованный вариант (зафиксировать в ADR): оставить на `Node` дешёвый флаг
`IsEventController` (читается в отрисовке каждый кадр), а тяжёлую часть — `StatusText`,
`Watched`, `WatchEventId`, `HasStatusLine` — перенести в отдельный `EventControllerState`
(или `ControllerState`), на который `Node` держит nullable-ссылку. Методы наблюдения из
`GridGraph` (`TryAddWatch`, `RemoveWatch`, `SyncWatched`, `MergeWatchIds`,
`PruneAdoptedWatchIds`, `CollectWatchedIds`) переезжают на этот тип (или в выделенный
`WatchList`-хелпер). `GridGraphBuilder.RefreshControllerState`, `EventControllerProbe`,
`EventControllerKeeper`, `NodeStateStore` (список в хранилище) и `PortGeometry` (жёлтые
полосы) правится под новое расположение. Это большая механическая правка — делать мелкими
коммитами, компилируя после каждого.

### 3.4. Офлайн-покрытие и документы

Перенести утверждения `OfflineChecks`, которые касаются `Watched`/`SyncWatched`, на новое
расположение. Обновить `03-architecture.md` (диаграмма: категория, `EventControllerState`)
и терминологию («специфика категории», «метрика состояния»).

### Критерий готовности Шага 3

- ADR принят (не черновик «в процессе»);
- 4 шлюза зелёные; `offline-check` покрывает новое расположение;
- `Node` больше не несёт `StatusText/Watched/WatchEventId/HasStatusLine`;
- `ResolveFamily` на подстроках заменён на `ResolveCategory`, деградация к generic-событию
  сохранена и покрыта офлайн-утверждением.

## Шаг 4 — Разбить `VgsEditorScreen` (P2)

**Цель:** физически разделить бог-класс (~4860 строк, 6 ответственностей) без изменения
поведения. Фундамент Этапов 5.1/5.2/5.4/5.5.

Два уровня, и их порядок важен — сначала дёшево и безопасно, потом глубже:

### 4.1. Частичные классы (механический, нулевой риск)

Разнести `VgsEditorScreen` на `partial`-файлы по секциям, которые уже намечены комментариями
`// ---- ... ----` в коде:

- `VgsEditorScreen.cs` — жизненный цикл + поля + конструктор;
- `VgsEditorScreen.View.cs` — состояние вида (камера/зум/режим) и `SaveView*`;
- `VgsEditorScreen.Input.cs` — `OnHandleInput`, режимы указателя, hit-test;
- `VgsEditorScreen.Search.cs` — поиск (клавиатура, каретка, буфер, `EnsureFieldLayout`);
- `VgsEditorScreen.Draw.cs` — `OnDraw` и все `Draw*`.

`partial` не уменьшает ответственностей класса, но делает его навигабельным и **не меняет
поведение вообще** — это безопасный первый шаг, после которого остальные правки идут по
файлам.

### 4.2. Выделить `SearchField` в отдельный тип (глубже)

Поиск почти самодостаточен: `TextEditor`, `TextClipboard`, `BlockSearch` уже вынесены.
Извлечь `Ui/SearchField.cs` — тип, владеющий `TextEditor`, кареткой/выделением, отрисовкой
`DrawSearchField`, hit-test и `HandleSearchKeyboard`/`PlaceCaretAtPointer`/`EnsureFieldLayout`.
Экран оставляет у себя только прямоугольник поля и прокси-вызовы. Это убирает ~600 строк из
класса и даёт прецедент для следующего шага.

### 4.3. Выделить `ViewState` (глубже)

Камера/зум/`showHidden` + троттлинг записи (`RememberSavedView`, `SaveViewIfChanged`,
`ViewChanged`, `SaveView`) — в `Ui/ViewState.cs` (или `Model`, если решить, что это данные;
решение — по ADR-0003: состояние вида — это не модель графа, а состояние экрана, поэтому
`Ui`). Экран держит `ViewState _view` и пробрасывает.

### Критерий готовности Шага 4

- 4 шлюза зелёные; `review-check` без находок R010 (нет новых аллокаций в кадре);
- класс разнесён по файлам; `SearchField` и `ViewState` — отдельные типы;
- поведение экрана не изменилось (регрессионный список прогнан человеком);
- `03-architecture.md`: диаграмма экрана обновлена под новые типы.

## Шаг 5 — Много-гридовой граф (P4)

**Цель:** позволить графу представлять блоки не только текущего грида, но и субгридов, с
идентичностью грида на узле и рамкой-группой на грид. Фундамент Этапа 5.5.

### 5.1. ADR: представление гридов

Зафиксировать решение: один `GridGraph` на конструкт (с `GridEntityId` на узле) против
список графов с общим холстом; как агрегировать видимость по гриду; где хранить видимость
грида (по аналогии с ADR-0015 «Show in VGS» агрегируется, ADR-0022 «состояние вида на
гриде»). Прецедент по обходу субгридов уже есть в `TerminalJump.HasBroadcastingAntenna`
(`grid.GetGridGroup(Logical).GetGrids`, `TerminalJump.cs:203-224`).

### 5.2. Идентичность грида на узле

В `Model/Node.cs` добавить признак грида (id/ключ), в `GridGraphBuilder` читать субгриды
логической группы и строить узлы с этим признаком; переиспользовать механику
рамок-групп (`PortGeometry.TryGroupFrame`, `LayoutGroupFrames`) для «рамки грида».

### 5.3. Видимость грида и отрисовка

Агрегированная видимость грида + переключатель «показать/скрыть грид» — по механике,
аналогичной группам; отрисовка рамки/переключателя — в слое Ui (после Шага 4 это отдельные
файлы).

### Критерий готовности Шага 5

- 4 шлюза зелёные; ADR принят;
- узлы субгридов попадают в граф и группируются рамкой по гриду;
- скрыть/показать грид не трогает связи (по правилу ADR-0013);
- `03-architecture.md` и терминология обновлены.
